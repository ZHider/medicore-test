## 三、质量检查结果

### 3.1 分层架构（spec §3.2 铁律）

| 检查项 | 结果 |
|---|---|
| 是否存在向上依赖（handler→repository、service→handler 等） | ✅ 无 |
| handler 层是否出现 GORM/SQL | ✅ 无（唯一命中是"本层禁止 GORM"这句注释本身） |
| service 层是否接触 `gin.Context` | ✅ 无 |
| GORM 是否只出现在 repository | ⚠️ 见下 |

**唯一偏离：`model` 包import了 `gorm.io/gorm`**，用于 PO 上的 `gorm.DeletedAt` 字段（5 处）。

保留理由：`gorm.DeletedAt` 让 GORM **自动为所有查询追加 `deleted_at IS NULL`**。
换成 `*time.Time` 就必须在每个查询里手写该条件——而我在 M3 已经踩过一次这样的坑
（手写 JOIN 不会自动带软删除条件，导致已删除医生出现在列表里）。用自动机制比靠人记得可靠。

这是**第 3 处刻意偏离 spec**，已在此记录。

### 3.2 死代码与坏味道

对全部生产代码的导出符号做引用计数扫描：

| 检查项 | 结果 |
|---|---|
| 零引用的导出符号 | ✅ 无（命中项均为"定义+使用各一次"的正常情况） |
| `panic(` | ✅ 无 |
| `TODO` / `FIXME` / `HACK` | ✅ 无（唯一命中是密钥特征检测器里的占位词列表） |
| `var _ =` 凑导入占位语句 | ✅ 无（**清理前有 4 处，均为我在开发过程中引入**） |
| 被忽略的错误 | ✅ 仅 6 处 `defer Close()`，属惯例写法 |

### 3.3 编码风格

`gofmt` 干净、`go vet` 零告警。

### 4.2 缺口分析（重要）

这个数字**低估了实际保障水平**，但也**暴露了真实盲区**：

**为什么 31.5% 不算差**：spec §11.1 要求的是"覆盖 service 层核心逻辑"，
而 service 达到 72.3%。抢号、对账、预问诊、认证的全部状态机分支都有断言。

**真实盲区有两个**：

1. **`repository` 6.8%** —— 1628 行 SQL 几乎只靠端到端验证。
   测试覆盖不到的地方包括：游标分页的边界、软删除条件是否遗漏、
   乐观条件的 `RowsAffected` 分支、`XAUTOCLAIM` 的真实行为。

2. **`handler` 0%** —— HTTP 适配层完全依赖端到端。

**为什么没有现在补**：这两层的单测需要真实 MySQL/Redis（或 sqlmock 的大量桩代码），
成本高而收益集中在回归保护上。当前用 `cmd/loadtest` + 逐模块端到端脚本覆盖了主路径，
但**这些脚本不会在 CI 里自动跑**，属于手工验证。

**建议**：M6 之前补一层"HTTP 集成测试"（`httptest` + 真实容器），
比给每个 repository 方法写 sqlmock 更有性价比。

## 五、依赖与安全

### 5.1 govulncheck 实测（spec §9.3 要求，此前未执行）

首次扫描发现 **6 个漏洞**：

| 漏洞 | 模块 | 修复版本 | 处置 |
|---|---|---|---|
| GO-2026-5676 | `quic-go v0.59.0` | v0.59.1 | ✅ 已升级 |
| GO-2026-4503 | `filippo.io/edwards25519 v1.1.0` | v1.1.1 | ✅ 已升级 |
| GO-2026-6355 | `x/crypto v0.54.0` | v0.56.0 | ✅ 已升级到 v0.57.0 |
| GO-2026-6354 | `x/crypto v0.54.0` | v0.56.0 | ✅ 同上 |
| GO-2026-6303 | `x/crypto v0.54.0` | v0.55.0 | ✅ 同上 |
| GO-2026-5932 | `x/crypto` | **N/A** | ⚠️ 官方无修复版本，且我们的代码未调用该路径 |

**注意 `x/crypto` 是我们的直接依赖**（bcrypt 就在其中），这 4 个漏洞不是"别人的问题"。

升级后复扫：**`No vulnerabilities found`**，且 bcrypt 与全部 158 个用例仍通过。

**遗留**：`GO-2026-5932` 无修复版本，只能接受并持续监控。
`govulncheck` 未纳入自动化，建议加入 `nub run backend:vet` 链路。

### 5.2 依赖面偏大（新发现）

```
直接依赖 15 个（含 miniredis/testify 等仅测试用）
go.mod require 行 68 条
编译进二进制的包 459 个
二进制体积 32.48 MB（linux/amd64，-s -w）
```

追查发现 **Gin v1.12 会传递引入两个与本项目无关的重型模块，且都真的被编译进二进制**：

| 模块 | 用途 | 我们的实际需要 |
|---|---|---|
| `go.mongodb.org/mongo-driver/v2` | Gin 的 BSON 绑定 | **不需要**（决策 #7 明确只用 Redis） |
| `github.com/quic-go/quic-go` | HTTP/3 支持 | **不需要**（只提供 HTTP/1.1 + SSE） |

这不是能用 build tag 关掉的（Gin 内部直接 import）。

**这解释了两件事**：一是二进制为什么有 32 MB，二是 `quic-go` 的漏洞为什么会进到我们的扫描结果里。
攻击面确实被无意中扩大了。

**建议**：接受现状（换路由框架的代价远大于收益），但在 README 与交付文档中**显式记录**这一事实，
并把 `govulncheck` 纳入常规检查——否则每次 Gin 引入的新 CVE 都会静默进入生产。

### 6.2 三处刻意偏离 spec（均有代码注释与文档说明）

| # | spec 原文 | 实际实现 | 理由 |
|---|---|---|---|
| 1 | `phone_hash = SHA256(phone+salt)` | HMAC-SHA256(pepper, phone) | keyed hash 更稳；输出同为 64 位十六进制，兼容 `CHAR(64)` |
| 2 | `internal/pkg/` 目录结构 | 工具包平铺于 `internal/` | `internal` 本身已阻止外部导入，`pkg` 是零语义的冗余层级 |
| 3 | "repository 是唯一允许出现 GORM 的层" | `model` 的 PO 使用 `gorm.DeletedAt` | 换取 GORM 自动软删除过滤，避免手写条件遗漏（已踩过坑） |

### 6.3 对 spec 缺陷的修正（4 处）

| # | spec 的问题 | 修正 |
|---|---|---|
| 1 | `schedules.status` 索引引用了不存在的列，建表必失败 | 补齐 `status` 列 |
| 2 | 抢号 Lua 在键不存在时返回 0（=号源不足），冷启动全盘失败 | 返回独立的 `-1`，先预热再重试 |
| 3 | 幂等键失败清理用无条件 `DEL`，会误删已完成记录 | 改为比对删除 |
| 4 | 医生-科室多对多后，排班唯一键未含科室，专家无法跨科室排班 | 唯一键加入 `department_id` |

## 七、结论与建议

### 做得扎实的部分

1. **分层纪律是真的**，不是写在文档里的口号——静态检查零违反。
2. **核心链路的分支覆盖充分**：抢号的 7 条失败路径、对账的双向偏差、
   预问诊的降级与重试，都有断言而非只测 happy path。
3. **关键安全属性有测试守护**：alg=none 伪造、时序侧信道（含反向验证）、
   幂等重放、超卖零容忍。
4. **修正了 spec 的 4 个缺陷**，且都用实测证明（不是"看起来对"）。

### 8.3 新增的两条不变量（含变异验证）

M6 引入了两条此前不存在的关键不变量。二者都做了**反向验证**——
先把实现改坏、确认用例确实变红，再还原：

| 不变量 | 变异方式 | 用例表现 |
|---|---|---|
| 同步绝不重置 `remaining` | `remaining = existing.Remaining + delta` → `remaining = in.Total` | `expected: 29, actual: 30` |
| 病历归属校验 | `view.PatientID != access.UserID` → `==`（判断写反） | 越权患者拿到 `200` 而非 `40302` |

第一条是 HIS 同步最典型的写法错误：把 `remaining` 与 `total` 一起覆盖，
等于**每次同步都把已预约的号源还回去**，每一次同步都是一次超卖。
第二条是双层校验里容易被忽略的一层——路由层只回答"是不是医生"，
回答不了"这次就诊归不归你"。

### 8.5 医生工作台补全这一轮的错误记录

| 错误 | 表现 | 根因 | 防法 |
|---|---|---|---|
| **测试 fake 被"简化"** | 把 map 形式的医生查询换成单值，直接弄坏了两个既有用例（`TestRecord_Write_RejectsOtherDoctorsPatient`、`TestRecord_Write_RequiresDoctorProfile`） | 改测试夹具时**只看了新用例的需要**，没跑全量 | 改夹具后**立刻跑全包**，而不是等写完新用例再跑 |
| **测试辅助函数重复定义** | `doctorAccess` / `patientAccess` / `adminAccess` 在 `record_test.go` 与 `appointment_doctor_test.go` 各写了一份 | 新文件是独立写的，没先搜一遍 | 新建测试文件前先 `grep` 一次辅助函数名 |
| **注释与实现矛盾** | `QueueItem.PatientName` 的注释写着"需要脱敏"，实现却是**刻意不脱敏** | 注释是早期写的，实现改了但注释没跟上 | 与实现矛盾的注释比没有注释更糟；改动实现时顺手扫一眼相邻注释 |
| **文档与实现脱节** | 管理端点漏写 `/admin/` 前缀；`POST /admin/sync/:source` 被列为"未完成" | 端点清单是手写的，没有从 `router.go` 生成 | **以 gin 启动输出为准**核对端点清单 |

最后一条是这一轮里代价最高的：照文档调接口会得到 404，
而**代码本身一直是对的**——错的只有文档。这与本项目"实测优先于文档推断"的性格一致：
凡是能从代码或运行时导出的清单，就不要手写。
