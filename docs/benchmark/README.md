# 性能基准（spec §12.2）

> **所有数字都是本机实测跑出来的**，不是推算或引用。
> 复现命令在各节给出；工具链版本见文末。

## 怎么读这份报告：先看"能说明什么"，再看数字

本机是 **Windows + Docker Desktop**，MySQL 与 Redis 都跑在容器里、
经由端口转发访问。这个环境有两点必须先讲清楚，否则下面的绝对值会被误读：

1. **绝对延迟被环境放大了。** 实测一次裸 `redis-cli PING` 往返要 **422 µs** ——
   在 Linux 上同宿主机的 Redis 通常是几十微秒。所以本报告里的微秒数
   **不能当作吞吐承诺**，它的用途是**同机对比**与**回归检测**。
2. **基准跑在 `-race` 关闭、单机、空负载的条件下。** 生产并发下的表现
   要看 `cmd/loadtest` 那套（见 `backend/README.md` 的并发压测一节）。

真正值得记住的是**相对关系**：谁比谁快一个数量级、什么改动会让耗时翻倍。
下面每一条都尽量给出这种可比的结构。

## 一、分页：游标 vs OFFSET

这是项目里最常被引用的一条结论（"为什么禁止 OFFSET"）。它现在有了可重复的基准。

```bash
cd backend
MEDICORE_BENCH_ROWS=200000 go test -tags=integration -run '^$' \
  -bench BenchmarkAuditList -benchmem -benchtime=20x ./test/integration/...
```

**环境**：`audit_logs` 表 20 万行，MySQL 8.0（容器内），每次取 20 条。

| 方案 | 页位置 | 耗时 | 内存/次 | 分配次数 |
|---|---|---|---|---|
| 游标 `WHERE id < ?` | 浅页（最新） | 1.21 ms | 33.7 KB | 692 |
| 游标 `WHERE id < ?` | 深页（很久以前） | **1.01 ms** | 37.4 KB | 692 |
| OFFSET | 浅页（OFFSET 0） | 1.02 ms | 16.9 KB | 451 |
| OFFSET | 深页（OFFSET ≈ 200k） | **38.81 ms** | 16.9 KB | 417 |

**结论（这才是要守的东西）**：

- 游标分页的代价**与翻到第几页无关**：深页 1.01 ms 甚至略快于浅页 1.21 ms。
- OFFSET 的代价**随深度线性增长**：同一张表、同样返回 20 行，深页比浅页慢 **38 倍**。
- 深页处两者相差 **38×**。

> ⚠️ **与另外两处测量的关系**：本项目对同一件事有三份数字，**口径各不相同，
> 都保留、不要互相覆盖**：
>
> | 出处 | 数据量 | 路径 | 深页倍数 |
> |---|---|---|---|
> | `docs/database-review.md` | 23 万行 | `EXPLAIN ANALYZE` | 284× |
> | **本报告** | 20 万行 | 端到端基准（经 GORM + 连接池） | **38×** |
> | `docs/sql-optimization.md` §3.1 | 30 万行 | `EXPLAIN ANALYZE`（客户端直连、热态） | 约 4300× |
>
> 差异来自数据量、OFFSET 深度、是否经驱动/连接池、以及冷热态。
> 三者共享的唯一可迁移结论是：**游标恒定，OFFSET 随页码线性增长**。
> 引用具体倍数时请连同测量条件一起引用。

**为什么游标那侧分配更多（692 vs 451）**：游标路径走的是生产代码
`AuditRepo.ListByCursor`（完整列 + `COALESCE`/`DATE_FORMAT` 映射到视图结构体），
OFFSET 那侧是为了做对照临时写的精简查询。**分配次数不可直接比较，耗时可比**。

## 二、号源扣减（Redis Lua）：抢号热路径

```bash
cd backend
go test -tags=integration -run '^$' -bench 'BenchmarkStock|BenchmarkRedisPing' \
  -benchmem -benchtime=2s ./test/integration/...
```

| 基准 | 耗时 | 说明 |
|---|---|---|
| `BenchmarkRedisPing` | **422 µs** | 基线：一次裸 Redis 往返 |
| `BenchmarkStockDecrement` | **419 µs** | 一次 EVALSHA 原子扣减 |
| `BenchmarkStockCompareAndSet` | **449 µs** | 对账用的比对更新 |
| `BenchmarkStockDecrementParallel`（4 并发） | 131 µs/op | 约 7,600 ops/s |

**结论**：

- **Lua 的开销可以忽略。** 扣减（419 µs）与裸 PING（422 µs）**在同一量级，
  差异在噪声内** —— 时间几乎全部花在传输上。这直接支撑了那条设计决策：
  **把 Lua 拆成多次调用是纯粹的损失**，往返次数翻倍，而且会破坏原子性。
- 并行后单次摊销成本从 419 µs 降到 131 µs（约 3.2×），说明瓶颈在往返延迟而非 Redis 本身。
- 对账的比对更新比扣减只多约 30 µs，尽管它多了一次 `GET` 与一个分支 —— 同样在一次往返内完成。

## 三、请求热路径（纯内存，不受环境网络影响）

这一节的数字**没有**上面的环境放大问题，可以直接横向比较。

### 审计写入（每个 HTTP 请求都会走）

```bash
cd backend
go test -run '^$' -bench . -benchmem ./internal/audit/
```

| 基准 | 耗时 | 内存 | 分配 |
|---|---|---|---|
| `Writer_Record`（正常入队） | 275 ns | 219 B | 5 |
| `Writer_RecordBufferFull`（缓冲满、丢弃） | **125 ns** | 80 B | 5 |
| `Describe`（路由模板 → 资源/动作） | 97 ns | 96 B | 1 |
| `truncate`（多字节 UA 截断） | 50 ns | 0 B | 0 |

**结论**：审计中间件对每个请求的总附加成本约 **370 ns**（Record + Describe），
量级正确 —— 这是"异步批量写"设计换来的：请求路径上没有数据库往返。

**背压路径比正常路径更快**（125 ns vs 275 ns）是**关键性质**：
缓冲满时走 `select` 的 `default` 分支直接丢弃 + 计数，
没有排队、没有阻塞。否则"数据库变慢"会演变成"全站接口变慢"。

### JWT（每个已登录请求都会校验）

```bash
cd backend
go test -run '^$' -bench . -benchmem ./internal/jwt/
```

| 基准 | 耗时 | 内存 | 分配 |
|---|---|---|---|
| `Manager_IssueAccess`（签发） | 3.58 µs | 2.7 KB | 40 |
| `Manager_Parse`（校验） | 4.38 µs | 2.3 KB | 42 |
| `Manager_ParseInvalid`（拒绝） | 0.64 µs | 608 B | 12 |

**结论**：校验约 **4.4 µs**，相对一次数据库往返（本机 1 ms 量级）可以忽略，
不构成中间件链的瓶颈。

**一个已评估的观察**：拒绝路径比通过路径快约 7 倍。这**不是**需要修的时序侧信道 ——
它只暴露"你自己的令牌格式不对"（客户端本来就知道，会收到 401），
不泄漏任何关于他人令牌或密钥的信息；而要伪造 HMAC-SHA256 签名本身不可行。
这里记下来，是为了说明**"看到差异 ≠ 发现漏洞"**，判断依据是它能被用来推断什么。

## 四、这些基准**不**测什么

诚实划界，避免把基准当保证：

| 没覆盖 | 为什么 | 那靠什么 |
|---|---|---|
| 生产并发下的真实吞吐 | 本机是单机 + 容器端口转发，数字不可外推 | `cmd/loadtest`（200 患者抢 20 号源，实测零超卖） |
| 连接的建立与池化行为 | 基准复用已建立的连接 | 压测 + 生产监控 |
| 数据库在数据量增长后的表现 | 只测了 20 万行这一个点 | 后续可按 `MEDICORE_BENCH_ROWS` 扫多个量级 |
| 前端性能 | 本报告只覆盖后端 | 尚未做 |
