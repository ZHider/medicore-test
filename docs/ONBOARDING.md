## 1. 先把它跑起来（约 15 分钟）

> 先看到东西在动，再讲道理。**跳过这节后面会很难受。**

### 1.1 需要装什么

| 工具 | 本机版本 | 它是干嘛的 | 为什么需要 |
|---|---|---|---|
| **Go** | 1.27.1 | 后端语言 | 后端是 Go 写的 |
| **Node.js** | 24.18.0 | 前端运行环境 | 前端是 Vue，靠 Node 跑构建工具 |
| **nub** | v0.9.0 | **本项目的包管理器** | ⚠️ **不是 npm/pnpm/yarn**，所有命令都是 `nub run xxx` |
| **Docker** | 29.7.2 | 跑 MySQL 和 Redis | 不用在宿主机装数据库，一条命令起容器 |

> **最容易踩的坑**：手贱敲 `npm install`。
> 那会产生第二份 lockfile、依赖树和项目不一致。**这个项目只用 `nub`。**

### 1.2 最短路径：四条命令

```powershell
# 1) 准备环境变量（只做一次）
copy .env.example .env

# 2) 起 MySQL + Redis（首次会自动执行 docs/schema.sql 建表）
nub run deps:up

# 3) 生成本地密钥（仓库里刻意不含任何密钥，只做一次）
cd backend; go run ./cmd/genlocal; cd ..

# 4) 灌演示数据（账号、科室、医生、排班）
nub run backend:seed
```

### 1.3 启动后端和前端

**开两个终端**（或者用一条命令，见下）：

```powershell
# 终端 A —— 后端，监听 127.0.0.1:8080
nub run backend:dev

# 终端 B —— 前端，监听 localhost:5173
nub run frontend:dev
```

或者**一条命令起三个进程**（依赖 + 后端 + 前端），`Ctrl+C` 一次全停：

```powershell
nub run dev
```

**验证后端活着**：

```powershell
curl http://127.0.0.1:8080/healthz
# {"code":0,"message":"ok","data":{"status":"ok"},"trace_id":"..."}
```

> ⚠️ **访问前端请用 `http://localhost:5173/`，不要用 `127.0.0.1:5173`** ——
> Vite 只监听 `localhost`，后者会"连接被拒"。这个坑真实存在，不是笔误。

### 1.4 用哪个账号登录

`nub run backend:seed` 会创建这些账号（**注意：没有患者账号**）：

| 角色 | 手机号 | 密码 |
|---|---|---|
| **管理员** | `13800000000` | `Admin@12345` |
| **医生** | `13900000001` ~ `13900000012` | `Doctor@123` |
| **患者** | —— | **要自己注册**（注册页随便填，只会得到患者角色） |

> **为什么没有患者账号？** 这是刻意的：医生和管理员**不能自助注册**
> （否则谁都能注册成管理员）。所以只能用数据脚本预置，患者则开放注册。
> 这个设计叫「防提权」，你在 §7 会再遇到它。

**登录后你会看到**：三种角色进入完全不同的界面。**建议三个都登一遍**，这是理解这个系统最快的方式。

### 1.5 想看成"生产形态"（可选）

上面是**开发模式**（两个进程 + 热重载）。还有一种**一键起全栈**的模式：
四个容器（MySQL + Redis + 后端 + nginx），前端产物被打进 nginx。**更接近真实部署**。

```powershell
nub run stack:init   # 生成 deploy/.env（随机密钥 + 探测空闲端口），只做一次
nub run stack:up     # 构建前端 + 构建镜像 + 起四个容器，并等它们全部健康
nub run stack:seed   # 灌演示数据
# 打开 http://127.0.0.1:8090
```

> **为什么是 8090 而不是 80？** 因为本机 80 端口被别的东西占着。
> `stack:init` 会自己探测空闲端口写进 `deploy/.env`，**不要写死端口号**。

### 1.6 数据乱了怎么办

```powershell
nub run deps:reset   # ⚠️ 会删数据卷，MySQL/Redis 全部清空
nub run deps:up
cd backend; go run ./cmd/genlocal; cd ..   # 密钥文件可能也没了
nub run backend:seed
```

## 2. 这个系统是干什么的（先说业务）

> **技术在 §3 才开始。** 如果你不理解业务，后面的代码会看不懂**为什么这么写**。

### 2.1 一句话

**MediCore 是一个"线上挂号 + AI 预问诊"的医疗系统。**
患者在家先跟 AI 聊清楚病情，AI 自动整理成一份结构化摘要；
医生在患者到诊前就能看到摘要，问诊效率更高。

### 2.2 三种人分别用它做什么

| 角色 | 他在这里干什么 |
|---|---|
| **患者** | 注册登录 → 找科室找医生 → 挑时间抢号 → 跟 AI 聊病情 → 提交 → 看 AI 整理的报告 → 就诊当天签到拿排队号 |
| **医生** | 登录 → 看今天接诊了谁（**哪些还没写病历**）→ 看候诊队列 → 看患者的 AI 报告 → 写病历 + 开处方 |
| **管理员** | 登录 → 看运营看板（预约趋势、科室热度、系统健康）→ 查审计日志 → 手动触发 HIS 数据同步 |

> **HIS** = 医院信息系统。真实医院里的医生/排班数据来自它。
> 这个项目用 `mockhis` 模拟了一个假的 HIS，管理员可以点一下"同步"来导入数据。

### 2.3 一次就诊的完整旅程

**把这条走通，你就懂了一半系统。**

```
患者侧
 1. 注册（手机号 + 姓名 + 口令）        → 得到 patient 角色
 2. 登录                              → 拿到两个令牌（access + refresh）
 3. 看科室 → 看医生 → 选日期看排班       → 看到"还剩几个号"
 4. 抢号                              → 生成预约，号源 -1
                                        15 分钟内是"待确认"，超时自动作废
 5. 跟 AI 预问诊对话                    → 你打字，AI 一个字一个字回（像 ChatGPT）
 6. 提交对话                          → 后端立刻回"收到了"，然后**后台慢慢整理**
 7. 看 AI 报告                        → 8 个字段：主诉、现病史、既往史、
                                        用药、过敏史、危险信号、建议科室、紧急程度
 8. 就诊当天签到                       → 拿到一个排队号（比如 7 号）

医生侧
 9. 打开工作台                        → 看到今天接诊的患者列表
                                        "没写病历"的会被标出来
10. 看候诊队列 + 看 AI 报告
11. 写病历 + 开处方                   → 写完，"未处理"标记消失

双方 + 管理员
12. 查病历（三种角色看到的东西不一样）
```

**第 6 步为什么是"后台慢慢整理"？** 因为 AI 生成要几秒到几十秒，
如果让用户在那儿干等，体验很差。这个设计叫「**异步**」，§7.4 会细讲。

## 3. 全局架构：四个盒子

### 3.1 四个盒子各干什么

```
   ┌──────────────┐
   │   浏览器      │   患者/医生/管理员在这里操作
   └──────┬───────┘
          │  HTTP 请求（都是相对路径 /api/v1/...）
          ▼
   ┌──────────────┐
   │  前端         │   Vue 3 + Element Plus + ECharts
   │  (Vue SPA)   │   负责：页面、交互、调接口、展示
   └──────┬───────┘
          │  开发：Vite 代理转发
          │  生产：nginx 反代
          ▼
   ┌──────────────┐
   │  后端         │   Go + Gin
   │  (Go 单体)   │   负责：业务规则、权限、事务、调 AI
   └───┬──────┬───┘
       │      │
       ▼      ▼
 ┌─────────┐ ┌─────────┐
 │  MySQL  │ │  Redis  │
 │ 事实来源 │ │ 加速+闸门│
 └─────────┘ └─────────┘
```

| 盒子 | 一句话职责 | **为什么非要它** |
|---|---|---|
| **Vue 前端** | 画界面、处理交互 | 用户看到的一切 |
| **Go 后端** | 所有业务规则 | **前端不可信** —— 抢号能不能成功、能不能看别人的病历，必须后端说了算 |
| **MySQL** | 唯一的事实来源 | 数据要永久保存、要能查、要能保证一致性（比如不能重复占号） |
| **Redis** | 缓存 + 原子闸门 + 队列 | MySQL 扛不住高频抢号；Redis 做"原子扣减"又快又不会超卖 |

> **"事实来源"是什么意思？** 就是"**以谁为准**"。
> 号源数字在 Redis 里也有一份（为了快），但如果两者不一致，
> **永远以 MySQL 为准**，然后用定时任务把 Redis 校准回去。这条规则很关键。

### 3.2 一次请求的完整旅程

以患者点"抢号"为例（`POST /api/v1/appointments`）：

```
1. 浏览器         axios 发出请求，自动带上 Authorization: Bearer <令牌>
2. Vite/nginx     同源代理，转发到后端 8080
3. TraceID 中间件  给这次请求生成一个追踪号（32 位十六进制）★
4. Recovery       兜住 panic，别让一个 bug 打挂整个进程
5. RequestLog     写一行访问日志（JSON，含追踪号）
6. Metrics        计数 + 耗时，给 Prometheus 抓取
7. RateLimit      限流（抢号：每用户每分钟 10 次）
8. JWT            验证令牌，解出"你是谁"
9. RBAC           检查角色（抢号必须是 patient）
10. handler       只做参数绑定与校验，不写业务逻辑
11. service       ★ 真正的业务：幂等检查 → 扣号源 → 事务落库 → 归属校验
12. repository    唯一可以碰数据库的层
13. MySQL/Redis   落库 / 原子扣减
14. Audit         记一条审计（谁、什么时候、访问了什么、成功没）
15. 返回统一信封   { code, message, data, trace_id }
```

**★ 标记的三处是重点**，后面都会讲。

> **中间件链的顺序不是随便排的**。比如：
> TraceID 必须在最前（后面所有日志都要用它）；
> Audit 必须在最后（这样"被 RBAC 拒绝的请求"也能被记录 ——
> 而"谁试图做什么但被拒绝了"恰恰是审计最关心的）。
> 顺序写在 `backend/internal/router/router.go` 里，有注释说明理由。

### 3.3 为什么没有"跨域（CORS）"问题

**新手常见困惑**：前端 5173、后端 8080，端口不同，浏览器不是会拦吗？

**答**：因为前端从不直连后端。前端只请求**自己的地址**：

```ts
// frontend/src/api/client.ts
const api = axios.create({ baseURL: '/api/v1' })   // 相对路径！
```

- **开发时**：`vite.config.ts` 配了代理，`/api/*` 转发到 `127.0.0.1:8080`
- **生产时**：nginx 同时托管前端文件**和**反代 `/api`

两种情况浏览器看到的都是**同源**，所以不触发跨域。

> **后端也确实没有任何 CORS 中间件** —— 这不是漏了，是**不需要**。
> 如果哪天要前后端分域名部署，那需要**后端加中间件**，属于后端改动。
> **别在前端用各种 trick 绕**（比如 JSONP），那是错的方向。

## 4. 后端：为什么必须分五层

### 4.1 五层的铁律

```
handler → service → repository → model
   ↑ 只能向下依赖，不能反向
```

| 层 | **只**做什么 | **绝不**做什么 |
|---|---|---|
| **handler** | 绑定参数、校验格式、调 service、返回响应 | ❌ 写业务逻辑 ❌ 出现 SQL 或 GORM |
| **service** | 业务规则、事务边界、权限归属校验 | ❌ 碰 `gin.Context`（HTTP 的东西） |
| **repository** | 数据访问（唯一允许出现 GORM 的层） | ❌ 业务判断 |
| **model** | 数据结构定义 | ❌ 任何逻辑 |

**为什么要这么麻烦？** 三个实际好处：

1. **可以单独测试业务** —— service 不依赖 MySQL/Redis，测试时注入"假的数据源"即可。
   这就是为什么 268 个后端用例能在几秒内跑完，不需要起数据库。
2. **换存储不用改业务** —— 如果哪天要从 MySQL 换掉，只改 repository。
3. **不容易写错权限** —— 权限校验有固定位置（service），不会散落在各处。

### 4.2 跟着"抢号"走一遍五层

**这是本文最值得精读的一段** —— 它把抽象的分层变成了具体的文件。

| 层 | 文件 | 在这里干了什么 |
|---|---|---|
| 路由 | `internal/router/router.go` | 声明 `POST /api/v1/appointments` 只允许 patient |
| **handler** | `internal/handler/appointment.go` | 把 JSON 解析成 `GrabRequest`，校验 `schedule_id` 存在。**仅此而已** |
| **service** | `internal/service/appointment.go` | **全部业务都在这里**：<br>① 幂等检查（这个 key 是不是已经处理过）<br>② 号源预检并原子扣减（Redis）<br>③ 数据库事务：建预约 + 扣号 + 记幂等结果<br>④ 失败要**回补 Redis**（否则号就凭空少了） |
| **repository** | `internal/repository/appointment.go` | 执行 SQL/GORM 操作，把 `gorm.ErrRecordNotFound` 翻译成 `ErrNotFound` |
| **model** | `internal/model/appointment.go` | 定义 `Appointment` 结构体、状态常量 |

> **注意 service 里那句"失败要回补 Redis"** —— 这是典型的"业务规则"，
> 它既不属于 HTTP 层，也不属于数据访问层。**这就是分层的意义**。

### 4.3 统一响应信封

**所有**接口（包括出错）都返回同一个形状：

```jsonc
// 成功
{ "code": 0, "message": "ok", "data": { /* 真正的业务数据 */ }, "trace_id": "3f2a…" }
// 失败
{ "code": 40002, "message": "号源不足", "data": null, "trace_id": "3f2a…" }
```

**三条必须记住**：

1. **业务数据在 `data` 里** —— 不是顶层。
2. **HTTP 状态码 ≠ 业务错误码**，是两套东西。
   **判定成功要用 `code === 0`，不要用 `status === 200`**。
   为什么？因为异步接口返回的是 **HTTP 202**，但 `code` 仍然是 0。
   （202 = "我收到了，还没处理完"）
3. **`trace_id` 是排障的唯一抓手** —— 界面上出错会显示
   `号源不足（追踪号 3f2a…）`，用户截图给你，你就能定位到那一条请求。

### 4.4 错误码怎么读

**不用背，记住规律就行**：

| 前缀 | 含义 | 例子 |
|---|---|---|
| `400xx` | 业务校验失败 | `40001` 参数错 · `40002` 号源不足 · `40003` 资源不存在 · `40005` 重复提交（其实是幂等，不是错） |
| `401xx` | 认证问题 | `40101` 没令牌 · **`40102` 令牌过期（可以自动续期）** |
| `403xx` | 权限问题 | `40301` 角色不够 · **`40302` 这不是你的资源** |
| `429xx` | 被限流 | `42901` 太快了，看 `Retry-After` 响应头 |
| `500xx` | 服务器问题 | `50001` 内部错误 · `50002` 依赖没就绪 |
| `502xx` | AI 上游问题 | `50201` AI 暂时不可用 |

> **`40101` 和 `40102` 必须分开处理**，这是新手最容易搞混的：
> 前者是"没登录/令牌坏了" → 直接跳登录页；
> 后者是"过期了" → **先尝试自动续期**，失败了才跳登录。
> 混在一起会让用户每两小时被踢一次。

## 5. 前端：目录与"点开一个页面发生了什么"

### 5.1 目录与职责

```
frontend/src/
├── api/           ★ 所有跟后端打交道的地方，按业务分文件
│   └── client.ts     唯一的 axios 实例（剥信封、自动续期、统一报错）
├── stores/        Pinia 状态（auth 登录态 / booking 挂号草稿）
├── router/        路由表 + 按角色动态注册 + 守卫
├── types/         ★ 后端数据的 TypeScript 类型定义（一 DTO 一个 interface）
├── composables/   可复用的逻辑（游标分页、倒计时、SSE 对话）
├── layouts/       AppLayout.vue —— 响应式外壳（宽屏侧栏 / 窄屏抽屉）
├── views/         页面
│   ├── patient/     患者：挂号、我的预约、AI 对话
│   ├── doctor/      医生：工作台、写病历
│   ├── admin/       管理员：看板、审计日志、HIS 同步
│   ├── ReportView.vue   三角色共用
│   └── RecordsView.vue  三角色共用
├── components/    可复用组件（图标、导航、状态标签、报告面板…）
└── utils/         纯函数工具（日期、SSE 解析、Prometheus 解析）
```

### 5.2 点开一个页面，发生了什么

以管理员刷新"运营看板"为例：

```
1. 浏览器请求 /admin/dashboard
2. 路由守卫 beforeRouterEnter 执行：
   a. 先问后端"我是谁"（GET /auth/me）← 关键！不信本地存的角色
   b. 已登录 → 先按角色注册路由（这一步顺序错了会 404，见下）
   c. 再检查这个页面允许不允许我的角色
3. 加载 DashboardView.vue
4. 组件在 onMounted 里调 api/admin.ts 里的函数
5. api 层走 client.ts → 自动带上令牌 → 发给后端
6. 后端返回信封 → client.ts 剥掉一层 → 组件拿到 data
7. ECharts 把数据画成图
```

> **⚠️ 这里有个真实踩过的坑，值得你知道**（写在 `router/AGENTS.md` §5.6.1）：
> 角色路由是**登录后**才注册的，所以**刷新页面时**目标地址会先被"万能匹配"接住。
> 如果守卫的**判断顺序写反**，就会直接放行 → 用户看到"页面不存在"。
> **正确顺序：已登录 → 先注册路由 → 再做其他判断。**
>
> 这个 bug 真发生过：**登录后能进看板，一按 F5 就 404**。
> 现在有 `router.spec.ts`（22 条用例）守着它。

### 5.3 三个"故意的设计"（别人看代码会疑惑的地方）

| 设计 | 看起来奇怪的地方 | **为什么这么做** |
|---|---|---|
| **`api/system.ts` 不走统一拦截器** | 别的 api 都走 `client.ts`，它自己发请求 | `/readyz`（健康检查）在依赖挂掉时返回 **503，但 `data` 里带着"哪个依赖挂了"的明细**。走拦截器会把这次响应压成"只有错误码、没有明细" —— 而明细正是运维要看的 |
| **`AppIcon` 是手写的 SVG 路径表** | 不用图标库？ | 引入图标库=新增依赖。而这里只需要十几个图标，手写一张表更轻 |
| **路由按角色动态注册** | 为什么不一次全注册？ | spec 的明确要求，也让"患者永远拿不到管理员页面的路由" |

> **共同点**：这三个都是"**看起来绕，其实是为了解决一个具体问题**"。
> 这个项目里这种地方很多，看到疑惑的先找注释——通常都写了为什么。

## 7. 五个"为什么"（**这节最值钱**）

> 会写能跑的代码只是及格。**能说清"为什么不那样"才是这个项目的重点。**
> 每条都按「现象 → 反过来做会怎样 → 所以怎么做」来讲。
>
> 这一节是**五个具体例子**；把它们抽成可迁移的通用原则的是
> **`docs/PRINCIPLES.md`**（分层 / 边界 / 数据 / 并发 / 错误处理 / 测试 / 工程习惯）。
> 读完本节后去那份文档，你会知道**下次遇到没见过的问题该怎么想**。

### 7.1 为什么号源既在 MySQL 又在 Redis？

**现象**：`schedules.total / remaining` 在 MySQL 里，但 Redis 里也存了一份计数。

| 如果只用 MySQL | 如果只用 Redis |
|---|---|
| 高并发抢号时，行锁排队 → 慢，甚至超时 | 数据会丢（Redis 是内存的），对不上账 |

**所以**：MySQL 是**唯一事实来源**（丢了要能恢复），Redis 负责**扛并发**（原子扣减，快且不会超卖）。
两者不一致时**以 MySQL 为准**，每 5 分钟有个定时任务按 MySQL 校准 Redis。

**这里还有三个不变量**（都在 `AGENTS.md` §2.4，值得专门看）：
1. 预热号源要用 `SETNX` 不是 `SET` —— 用 `SET` 会把并发已经扣掉的号"还回去"，直接超卖
2. **键不存在 ≠ 号源不足** —— 是"还没预热"，要先去预热再重试，不能告诉用户"没号了"
3. 回补号源要有上限 —— 否则 `INCRBY` 能凭空虚造出号来

### 7.2 为什么分页用"游标"而不是"页码"？

**现象**：所有列表接口只接受 `cursor` + `size`，**没有 `page` 参数**。

| 页码分页（`LIMIT 20 OFFSET 300000`） | 游标分页（`WHERE id < 上一页最后一个id`） |
|---|---|
| 数据库要把前 300000 行**全部读出来再扔掉** | 直接定位，只读 20 行 |
| 实测：读 30 万行 / **94.2 毫秒** | 实测：读 21 行 / **0.022 毫秒** |

**差了 3 个数量级。** 而且页码分页在数据变化时会**重复或漏掉**记录。

**所以**：用游标。**三个容易写错的地方**：
- 判"还有没有下一页"要用 `has_more`，**不要**用 `items.length === size`
  （最后一页刚好满页时会多请求一次）
- `next_cursor` 没有下一页时**这个字段会整个消失**（不是 null），要按可选处理
- 不要在前端去重后再拼接（游标天然不重复）

### 7.3 为什么手机号脱敏，患者姓名却不脱敏？

**现象**：`GET /auth/me` 返回的手机号是 `138****8888`，
但医生工作台里的患者姓名是**完整的**。

**这不是 bug，是刻意的**：

| 字段 | 脱敏? | 理由 |
|---|---|---|
| 手机号 | ✅ | 敏感，医生不需要靠它认人 |
| 医生姓名 | ❌ | 医生信息公开 |
| **患者姓名** | ❌ **刻意不脱敏** | **医生必须能认出面诊的是谁**。打成"张*"会让候诊队列彻底失去意义 |
| 身份证 | —— | **从不返回**（只在注册时收） |

**那患者隐私怎么保护？** 靠**资源层归属校验**：
医生只能看到**自己接诊**的患者，换个别人的预约 ID 会拿到 `40302`。

> **所以：前端不要自作主张给患者姓名打码** —— 那会破坏医生工作台的核心用途。

### 7.4 为什么 AI 总结是"异步"的？

**现象**：患者提交对话，后端**立刻**返回 HTTP 202（"收到了"），
但报告要过几秒才出现，前端在**轮询**。

**如果同步等待**：AI 要生成几秒到几十秒，用户就卡在那儿转圈；
更糟的是，如果 AI 挂了，整个请求就失败了。

**所以**：
```
提交 → 建一份"待处理"的报告 → 丢进 Redis 队列 → 立刻返回 202
                          ↓（后台独立进行）
                     worker 取出来 → 调 LLM → 校验格式 → 写回结果
```

**前端要处理三种终态**（这是最容易漏的）：

| 情况 | 怎么判断 | 该展示什么 |
|---|---|---|
| 正常 | `status === 'done'` 且 `fallback === false` | 渲染结构化摘要 |
| **降级** | `status === 'done'` 且 **`fallback === true`** | AI 没总结出结构 → **展示原始对话** + 标注"未能结构化总结" |
| 失败 | `status === 'failed'` | 展示错误原因 + 提供重试 |

> **"降级"这条最容易漏**：如果只判断 `status === 'done'` 就去读结构化字段，
> 遇到降级时字段是空的 → **页面白屏**。

### 7.5 为什么用 `nub`，容器还不出网？

**为什么不用 npm？** 会产生第二份 lockfile，依赖树和项目不一致。
**这个项目统一用 `nub`**（`nub run xxx`）。

**为什么容器不出网？**
- 容器里 `GOPROXY=off`：缺依赖会**立刻**报错（0.03 秒），
  而不是等 15 秒超时后报一个让人误解的网络错误
- **不给容器配代理**：`127.0.0.1` 在容器里指向容器自己；
  写 `host.docker.internal` 等于把某个人电脑上的代理变成**所有人（含 CI）的构建依赖**
- 如果那个代理是**按流量计费**的，每次构建都在花别人的钱

> ⚠️ **所以：加任何依赖之前先问。** 这不是保守，是**这个动作会出网、会花钱**。
> 想加依赖的规范说法是：「要什么 + 为什么现有依赖做不到」。

### 8.1 排障三步

```
① 看界面上的错误提示 + 追踪号
      ↓
② 拿追踪号去查这条请求发生了什么
      ↓
③ 还没头绪 → 看 §10 的文档地图，找对应模块的说明
```

### 8.2 追踪号怎么用（**最实用的技能**）

界面报错会显示 `号源不足（追踪号 3f2a1b…）`。**这个号能定位到那一次请求。**

```powershell
# 方式一：界面查（需要管理员账号）
# 管理看板 → 审计日志 → 追踪号输入框，粘贴进去

# 方式二：直接查数据库（后端挂了也能用）
node deploy/db.mjs mysql "SELECT method, path, status_code, latency_ms, created_at FROM audit_logs WHERE trace_id='把追踪号粘这里'"

# 方式三：搜后端日志
# 后端日志是 JSON，输出在终端里（没写文件）
nub run backend:dev 2>&1 | Select-String "把追踪号粘这里"
```

### 8.3 常见现象 → 先查哪里

| 现象 | 第一反应 |
|---|---|
| 页面打不开 / 白屏 | 打开浏览器 F12，看 Console 报错 + Network 里哪个请求失败 |
| 点了按钮没反应 | **多半是"目标路由没注册"或"接口 403"**（§5.2 那个坑）|
| 接口返回 40302 | 这是"**这不是你的资源**"，不是权限不够。换个自己的 ID 试试 |
| 接口 401 但令牌看着没过期 | 看 `expires_in`（2 小时）和系统时间；正常情况会自动续期 |
| 登录提示"密码错误"但其实没输错 | 可能是**被限流**了（5 次/分钟）—— 限流不该提示密码错误 |
| 数据不对/乱了 | `nub run deps:reset` 重来（⚠️ 会删数据） |
| 后端改了代码没生效 | 后端**没有热重载**，要重启 `backend:dev` |
| 改了 `vite.config.ts` 没生效 | Vite 只热更新源码，**配置改动要重启** `frontend:dev` |

## 9. 术语表

新手最容易卡住的词，按出现顺序：

| 术语 | 白话解释 |
|---|---|
| **信封（envelope）** | 所有接口返回的统一外壳 `{code, message, data, trace_id}`，业务数据在 `data` 里 |
| **trace_id / 追踪号** | 每次请求的唯一编号，贯穿日志和审计，是排障的抓手 |
| **中间件（middleware）** | 请求到达业务代码**之前**要经过的一道道关卡（认证、限流、日志…） |
| **RBAC** | 基于角色的权限控制（"你是什么角色"） |
| **资源层归属校验** | （"这个资源是不是你的"）—— 和 RBAC 是两回事，别混 |
| **游标分页（cursor）** | 用"上一页最后一条的 ID"翻页，比"第 N 页"快几个数量级 |
| **幂等（idempotent）** | 同一个操作做多次，结果和做一次一样。抢号靠"幂等键"实现 |
| **幂等键** | 一次提交的唯一编号。重试要**复用同一个**，用户重新点击要换新的 |
| **事务（transaction）** | 一组数据库操作要么全成功、要么全失败 |
| **SSE** | 服务器持续往浏览器推数据的技术，AI 打字机效果就靠它 |
| **异步 / 轮询** | "先回执、后处理"，前端隔一会儿问一次"好了没" |
| **降级（fallback）** | AI 没成功时的备用方案：展示原始对话而不是结构化摘要 |
| **脱敏** | 把敏感信息打码（`138****8888`） |
| **密封/加密** | 数据在数据库里是密文，不是明文 |
| **SPA** | 单页应用。整个站点只有一个 HTML，切换页面靠 JS |
| **动态路由注册** | 登录后才知道你的角色，再决定注册哪些页面 |
| **HIS** | 医院信息系统。真实医院里医生/排班数据的来源 |
| **事实来源（source of truth）** | "以谁为准"。本项目是 MySQL |
