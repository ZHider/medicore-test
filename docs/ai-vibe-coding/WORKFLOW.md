# WORKFLOW —— 实际走的工作流，与 spec §10.1 的差异

> **一句话**：spec §10.1 的五步流程**大体走了**，但有三处实质偏离，
> 而且真正抓出缺陷的是 spec 里**没有**的两步。
> 本文档把"应该怎么走"和"实际怎么走"并排写出来，差异逐条标注，不粉饰。

---

## 一、spec §10.1 的五步，逐条对照

| # | spec 要求 | 实际做法 | 判定 |
|---|---|---|---|
| 1 | 需求拆解 → 模块化 mini-spec | 以 `spec.md` 的分节为模块边界（§3 架构 / §5 数据库 / §6 API / §7 核心流程 / §9 非功能），逐模块开工前把对应小节摘出来对齐；**没有另写 mini-spec 文档** | ⚠️ 部分达成 |
| 2 | 给出 2–3 套方案 → 人工按 KISS/性能选定 | 关键决策确实做了多方案权衡，但**不是每个模块都做**，也没有留下"2–3 套方案"的并列文档；权衡结论散落在代码注释与 `MODULES.md` 的"关键决策"表里 | ⚠️ 部分达成 |
| 3 | 按 `prompts/system-rules.md` 生成代码 | **这个文件从未存在过。** 全局规则的实际载体是 `AGENTS.md`（版本化在 git 里、由 agent 自动读取，而不是每次对话粘贴） | ❌ 偏离（更好的载体） |
| 4 | 人工 Review → 产出 review 记录 | Review **确实做了**（两轮全量审视 + 一次按角色横切），但产出物是 `HANDOVER.md` / `FIXES.md` / `PITFALLS.md`，**不是逐模块 review**。本目录是事后补的归档 | ⚠️ 部分达成 |
| 5 | 跑测试 → 失败信息回喂修正 | **达成，而且是产出最高的一步**。见下面 §三 | ✅ |

### 差异 1：全局规则用 `AGENTS.md` 而不是 `prompts/system-rules.md`

`AGENTS.md` 与 spec 设想的 system prompt 是**同一个东西**，只是换了载体：

| | spec 设想 | 实际（`AGENTS.md`） |
|---|---|---|
| 形态 | 一段贴进对话的提示词 | 仓库里的一个文件 |
| 版本 | 靠对话历史 | **git 版本化**，与代码同提交 |
| 生效 | 每次手工粘贴 | agent **自动读取**，不会漏 |
| 内容 | 分层铁律 + 质量约束 | 分层铁律 + **踩过的坑 + 检查清单 + 项目性格** |

实际版本**更强**：它不只写"应该怎么做"，还写了**每条规则是从哪个坑里长出来的**
（例如 §2.4 的三条 Redis 号源不变量，每条都对应一次真实的超卖风险）。
`docs/ai-vibe-coding/prompts/system-rules.md` 因此**只做指针，不复制内容** ——
复制必然与 `AGENTS.md` 漂移，而漂移的规则文件比没有规则文件更糟。

### 差异 2：Review 的产出物形式

spec 想要"每个模块一篇 review"。实际做成了**横切的三份文档**：

```
HANDOVER.md §2   —— 按时间线的原始错误记录（含"当时为什么会犯"）
FIXES.md         —— 按严重度的缺陷总账 + 当前健康指标
PITFALLS.md      —— 按类别的易错点 + 诊断判据
```

**这个形式有得有失**：好处是"同类问题成体系"（第 7 条项目性格：
发现一处归属校验漏洞就把所有返回他人数据的端点扫一遍），
坏处是**按模块回溯时要翻三份文档**。本目录的 review 就是补这个缺口。

### 差异 3：缺少"每模块 2–3 套方案"的并列记录

实际发生的方案权衡（下表），但**都是在对话里定的，没有留下并列的备选方案文档**：

| 决策点 | 被否决的方案 | 选定 | 理由（真实写在代码注释里） |
|---|---|---|---|
| 刷新令牌 | JWT（自包含、无状态） | **不透明随机串 + Redis** | 刷新令牌**必须可撤销**；既然要存 Redis，JWT 的自包含性毫无收益 |
| 刷新消费 | `GET` + `DEL` | **`GETDEL`** | 两步写法在并发刷新时同一令牌会被消费两次 → 重放窗口 |
| 号源扣减后落库 | 读 `version` → 比对 → 写回 | **单条原子 `UPDATE`** | InnoDB 行锁下 `remaining > 0` 即是充分条件；省一次 SELECT 且无需重试循环 |
| LLM 流式接口 | channel | **回调（callback）** | channel 会重新引入 goroutine 泄漏风险；回调的返回错误天然表达"客户端已断开" |
| 预问诊总结 | 同步等 LLM 返回 | **异步（Redis Stream）** | 真实场景里用户提问后会刷新页面；且 LLM 有限流时必须能排队 |
| 审计写入 | 同步写（永不丢） | **异步批量 + 有界缓冲** | 审计是事后追溯用途，不在关键路径；代价（崩溃丢一个批次）已明确记录 |
| 医生/科室关系 | 一对多（`doctors.department_id`） | **多对多（`doctor_departments`）** | 专家跨科出诊；同时使排班唯一键必须含 `department_id`（spec 原设计漏了这一列） |
| 列表分页 | OFFSET | **游标（`id < cursor`）** | spec §5.2 强制；实测深页差 38×–4300×（口径见 `docs/sql-optimization.md` §0） |
| 模拟 HIS 数据源目录 | `pkg/mockhis`（spec 原文） | **`internal/his` 契约 + `mockhis` 适配器** | 原设计让 `service` 依赖了一个名字里带 mock 的包，那个"抽象"什么也没抽象 |

> **这张表本身就是交付物的一部分**：它把"当时比较过什么"补记下来。
> 但**必须说清它是事后整理的**，不是当时的会议纪要。

## 二、spec 里没有、但实际最管用的两步

### 第 6 步（补充）：**独立验证**，而不是只跑测试

测试全绿是**必要不充分**条件。本项目另外做了三件事，抓到的缺陷多于测试本身：

| 手段 | 抓到了什么 | 为什么测试抓不到 |
|---|---|---|
| **反向验证**（改坏实现，看测试是否变红） | 3 处"看起来在断言、其实恒为真"的测试 | 恒真的断言**永远是绿的**，只有改坏实现才能证伪它 |
| **Fuzz**（11 个目标） | 2 个真实缺陷：`truncate` 遇非法 UTF-8 原样返回毒掉整批插入；`IDCard` 在长度恰为 10 时一个字符都没屏蔽 | 手写测试想不到"输入本身就是非法 UTF-8"、也想不长度恰好为 10 |
| **静态检查**（`vet` / `staticcheck` / `deadcode` / `golangci-lint`） | 死代码、不可达分支、`sync_logs.trace_id` 从不写入、11 条文档缺口 | 测试不关心"这段代码有没有人调用" |

**更要紧的一条**：这些手段本身也会**静默失效**。
`backend/scripts/race.sh` 曾经在 `nub run` 路径下"返回成功但一次都没跑"
（1 秒、退出码 0、零输出）—— 见 `docs/HANDOVER.md` §2.10。
所以现在对每个检测类命令都加了**产出断言**：
**"如果它什么都没做，我会看出来吗？"**

### 第 7 步（补充）：**按角色横切复查**，而不是按模块

M1–M6 全部标记"完成"之后，把 spec §2.1 的角色能力矩阵**横过来**查了一遍，
发现医生侧有**两处真实缺口**（`GET /doctor/appointments`、报告未对医生开放）。

> **教训：模块维度全部打勾 ≠ 角色维度没有缺口。**
> 逐模块自测时，M4 自测通过、M5 自测通过，但"医生坐下来用一遍"这条路径
> 从来没被完整走过。

后续把患者、管理员两个角色也这样查完了 —— 结论是**无新缺口**
（逐端点的证据表见本轮提交说明与 `AGENTS.md` §8）。

## 三、第 5 步（测试反馈）为什么是产出最高的一步

失败信息回喂修正是本项目**唯一稳定有效的缺陷来源**。具体形态有三种：

| 形态 | 例子 |
|---|---|
| **测试失败 → 发现实现错了** | 抢号 `recoverDuplicate` 把任何错误都当"重复抢号"报 409 —— 数据库抖动被说成"您已预约"，真实原因既没包装也没日志 |
| **测试失败 → 发现测试错了** | 断言 `{}` 应该编译失败 —— 但 **`{}` 是合法的 JSON Schema**。这次"测试错"反而暴露了一个真实风险（Schema 被改成空对象会让校验静默失效），于是加了 `SelfCheck()` 把陷阱变成启动即失败 |
| **测试间歇失败 → 发现夹具错了** | 约 1/3~1/5 概率红一次，且**每次报错的用例都不同**；根因是夹具生成器用 `time.Now().UnixNano()%100000` 拼唯一键，生日悖论下必撞。改用 `atomic.Uint64` 计数器 —— 从概率保证变成构造性保证 |

> **判据**：Error Trace 指向**断言** → 用例逻辑问题；指向**建数据**（`seed*`）→ 夹具问题。
> 后者不要改用例，要改生成器。

## 四、这个工作流的**主要失效模式**

跨所有轮次统计的结论（`docs/PITFALLS.md` §11）：

> **设计判断通常站得住，出问题的是收尾动作。**

| 类别 | 次数 | 形态 |
|---|---|---|
| 凑导入占位（`var _ = x`） | 4 | 写完不编译 |
| 写了占位文件当完成 | 3 | 写下一个时注意力已转移 |
| 注释描述尚不存在的实现 | 2 | "故障会被 metrics 捕获"而当时没有那个指标 |
| 测试看起来在断言、其实恒为真 | 3 | 断言夹具静态字段，而非行为 |
| fuzz 报失败但其实是我的断言错 | 3 | 提了实现做不到的要求 |
| **脚本返回成功但其实什么都没做** | 1 | `race.sh` 静默通过（最难发现的一类） |

**三条能挡住绝大多数**：

```
① 每写完一个文件立刻编译        —— 8 个自我引入的错误里 5 个会被这一步拦下
② 关键测试做反向验证            —— 唯一能证伪"测试在说谎"的方法
③ 检测类命令加产出断言          —— 让"什么都没做"不可能伪装成成功
```

## 五、给想复用这套流程的人

**值得保留的**：

1. **全局规则写成仓库里的文件**（`AGENTS.md`），而不是对话里的提示词 ——
   版本化、自动加载、不会漏，而且可以承载"这条规则是从哪个坑来的"。
2. **反向验证**：任何关键测试写完，故意改坏实现确认它会红。
   **没有反向验证过的测试，不能算测试。**
3. **按角色横切复查**，作为模块验收之外的独立一轮。
4. **把"实测"当成唯一的结论来源**：TS7 不可用、分页倍数、依赖漏洞、
   索引该不该留 —— 全部是跑出来的，不是查文档得出的。
5. **发现一处同类问题就成体系排查**，而不是等它一个个冒出来。

**需要警惕的**：

1. **不要为了凑"每模块 2–3 套方案"而编造并列方案**。
   真正做过权衡的决策能写清楚"为什么否掉另一个"；没做过的就写清楚没做。
2. **不要倒填档案日期**。本目录的 review 是事后整理的，
   每一篇都标明来源 —— 这比一份看起来完美的即时档案更经得起追问。
3. **主要风险不在设计，在收尾**。写完不编译、写了不跑、断言恒为真 ——
   这三件事与设计能力无关，但它们构成了本项目绝大多数缺陷。
