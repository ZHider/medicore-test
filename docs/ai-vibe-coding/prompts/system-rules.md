# 全局规则提示词（`prompts/system-rules.md`）

> **这个文件是指针，不是内容。**
> 全局规则的实际载体是仓库根的 **`AGENTS.md`**。
> 复制一份到这里会让两份规则各自演化，而**漂移的规则文件比没有规则文件更糟** ——
> 它会让人以为读了就是遵守了。

## 为什么不在这个位置

spec §10.3 设想的目录结构是：

```text
docs/ai-vibe-coding/
└── prompts/
    └── system-rules.md      # 全局规则提示词
```

即"一段贴进对话的提示词"。本项目换成了仓库里的一个文件，理由是它的性质不同：

| | 贴进对话的提示词 | `AGENTS.md` |
|---|---|---|
| 版本化 | 靠对话历史，找不回上一版 | **与代码同提交**，可 `git log -p` |
| 生效方式 | 每次手工粘贴 | 由 agent **自动读取**，不会漏 |
| 规模 | 受上下文预算限制，只能写要点 | 566 行，可以写**每条规则背后的坑** |
| 一致性 | 每次粘贴可能微调，逐渐漂移 | 单一副本，改一处即全局生效 |

## 实际规则在哪、写了什么

| 章节 | 内容 |
|---|---|
| `AGENTS.md` §0–§1 | 项目是什么、当前状态、上手三件事 |
| **§2 硬性规则** | 分层铁律 / 接口由使用方定义 / 缓存回源脱离取消 / Redis 号源三条不变量 / 手写 JOIN 带软删除 / **密钥绝不进仓库** / **引入新依赖前必须先问** |
| §3 架构 | 目录结构、中间件链、存储职责、关键数据流 |
| §4 常用命令 | `nub run` 各任务的入口 |
| **§5 已知陷阱** | 13 条，每条都有"当时怎么踩的" |
| **§6 检查清单** | 提交前逐项自查（含"没有自行引入新依赖"） |
| §7 项目性格 | 实测优先 / 测试必须能失败 / 注释解释为什么 / 偏离 spec 要标注 |
| §8 下一步 | 未完成的工作与优先级 |

**其中 §2 与 §6 才是真正的"system rules"**：前者是禁令，后者是可执行的自查项。
`docs/PITFALLS.md` 则是它的展开版（四张诊断判据表 + 按类别的防法）。

## 与"AI 幻觉"检查的关系

`AGENTS.md` §6 的检查清单里**没有**"调用的库函数是否真实存在"这一条，
原因是本项目实测下来它**不需要**：

> 不存在的符号在**编译期**就会被拦住，根本活不到提交。
> 真正需要防的是**"符号存在但语义记错"**（参数含义、返回约定、边界行为）——
> 那类靠反向验证与集成测试抓。

本轮做过一次全量核对：从源码抽出 110 个「包.符号」引用逐个 `go doc` 验证，
**真实幻觉 0 个**（详见 `docs/ai-vibe-coding/README.md` 的"关于第六项"）。
