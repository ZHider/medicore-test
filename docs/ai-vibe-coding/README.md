# AI Vibe Coding 过程留痕（spec §10.3 / G6）

> **这份目录的性质，先说清楚，避免误读。**
>
> 它**不是**开发当时逐字记录的、按 spec §10.1 五步生成的原始档案。
> 本项目的开发过程确实由 AI 主导，但当时的留痕散落在
> `docs/HANDOVER.md`、`docs/FIXES.md`、`docs/PITFALLS.md`、git 提交历史与代码注释里，
> **没有同步写成 review**。这个目录是**事后整理**的：
> 把已有的真实证据归拢成逐模块 review，并对 §10.2 里当时没系统查过的项**现在补查**。
>
> 每一篇 review 的头部都标明了**每一项结论的来源**（哪个提交 / 哪份文档 / 本次新查）——
> 读者应该能凭那个来源自己复核，而不必相信本文档的叙述。
>
> **为什么不假装是当时写的**：这个项目的一贯立场是
> "实测优先于文档推断"（`AGENTS.md` §7 第 1 条），
> 以及"把'打算做'写成'已完成'"被明确列为易错点（`docs/PITFALLS.md` §9）。
> 一份为了满足验收清单而倒填日期的档案，恰好违反这两条。

## 每篇 review 的固定结构

spec §10.2 要求「**每篇 Review 必含**」六项检查清单。六篇一律按下列结构写，
六项清单**逐项出现，不允许因为"这模块用不上"而省略** —— 写"该项不适用，理由是…"
本身就是一次检查：

```markdown
# 0N · M<N> —— 模块名
  （头部表：对应提交 / 规模 / 本篇性质与来源 / 结论）

## 一、需求拆解        ← spec §10.1 第 1 步的回顾，含"spec 有缺陷需修正"的部分
## 二、方案选型        ← spec §10.1 第 2 步的回顾，含被否决的方案
## 三、§10.2 检查清单（六项）
   ① 分层与架构   ② 错误与并发   ③ 性能与 SQL
   ④ KISS 原则    ⑤ 基础卫生     ⑥ AI 幻觉
## 四、本模块暴露的真实缺陷
## 五、反向验证记录    ← "改坏实现会不会红"
## 六、遗留与未验证
```

## 关于第六项「AI 幻觉」的验法

spec 的原文是「调用的库函数/参数是否真实存在（**对照官方文档**）」。
本项目采用了一个**比查文档更硬**的办法：

> 依赖源码就在本机 Go module 缓存里。**读真实源码 / 用 `go doc` 反射**，
> 而不是凭记忆或检索文档。

本轮实测范围与结果：

| 项 | 数 |
|---|---|
| 源码里 import 的第三方包 | **21 个** |
| 从源码抽出的「包.符号」引用 | 110 个组合 |
| `go doc` 验证**存在** | **101** |
| 剩余 9 条经人工核实为**抽取假阳性** | 8 条是 `v.SetDefault("mysql.host", …)` 这类**配置键字符串**，1 条是 import 路径里的 `gorm.io/gorm` |
| **真实幻觉** | **0** |

方法可复现（在 `backend/` 下）：抽取 `alias.Symbol` 后用 `go doc <importPath>.<Symbol>`
逐个验证，退出码非 0 即候选幻觉，再人工排除正则假阳性。

> **这个结果不等于"AI 没编过 API"**：编译期就能拦住不存在的符号，
> 所以幻觉一旦发生会立刻暴露、根本活不到提交。
> 真正需要防的是**"符号存在但语义记错"**（参数含义、返回约定、边界行为）——
> 那类只能靠反向验证与集成测试抓，见各篇 §五。
