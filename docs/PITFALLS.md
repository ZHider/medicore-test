# 易错点手册

> **给写代码和写测试的 agent。** 这份文档不重复讲细节，它做三件事：
>
> 1. **按类别归纳**所有已知易错点（细节在原文档，这里给链接）；
> 2. 给出**诊断判据** —— 出问题时先判断它属于哪一类，再去看对应条目；
> 3. 每条都写**防法**，即"下次怎么做才不会重蹈"。
>
> 详细的"当时是怎么发生的"在 `docs/HANDOVER.md` §2；
> 完整的缺陷与修复账在 `docs/FIXES.md`。

---

## 0. 先看这里：四张诊断判据表

出问题时的第一动作不是改代码，而是**判断它属于哪一类**。判断错了，后面全错。

### 判据 1 · 测试挂了，是用例的问题还是代码的问题？

| 现象 | 归类 | 去哪 |
|---|---|---|
| Error Trace 指向**断言行** | 用例逻辑 or 被测代码 | 本文件 §6 |
| Error Trace 指向**建数据**（`insertAndLastID` / `seed*`） | **夹具/测试基建** | 本文件 §7 |
| 单跑通过、全量失败；或每次失败的用例都不同 | **测试污染或 flaky** | 本文件 §7 |
| 反向验证时（改坏实现）用例**依然绿** | 测试根本没在断言 | 本文件 §6 |
| fuzz 报失败 | **先怀疑断言**，再怀疑代码 | 本文件 §6 |

### 判据 2 · 并发问题的三种形态

| 现象 | 大概率是 | 去哪 |
|---|---|---|
| 恢复/兜底逻辑"从不生效" | **复用了已取消的 context** | §2 |
| 间歇失败、单跑复现不了 | 时序依赖，且**等待条件不等于断言目标** | §7 |
| 数据偶尔不一致但没有报错 | **读-写之间的时间窗**（对账、回补） | §3 |

### 判据 3 · 数据不一致

| 现象 | 大概率是 | 去哪 |
|---|---|---|
| 号源"凭空变多" | 回补没做容量上限 / 无条件 `SET` | §3 |
| 号源"越来越难抢" | 回补或对账路径被跳过 | §3 |
| 已删除的行出现在结果里 | 手写 JOIN 没带软删除条件 | §4 |
| 空列表返 `null` 而不是 `[]` | 没走 `model.NonNil` | §4 |

### 判据 4 · 这条改动该动哪一层？

| 想做的事 | 必须放哪 | 去哪 |
|---|---|---|
| 校验"这个资源是不是你的" | **service**（路由 RBAC 做不到） | §5 |
| 写 SQL | **repository** | §1 |
| 定义 service 需要的能力 | `service/deps.go` 的接口 | §1 |

## 1. 分层与架构

| 易错点 | 症状 | 防法 |
|---|---|---|
| handler 里写 SQL/GORM | 分层破裂，SQL 散落各处 | 改完跑 `grep -rn "gorm.io/gorm" internal/handler` |
| service 里碰 `gin.Context` | service 无法脱离 HTTP 测试 | `grep -rn "gin.Context" internal/service` |
| 直接依赖 `*repository.XxxRepo` | service 单测被迫起数据库 | 在 `deps.go` 加最小能力接口 + 内存 fake |
| **接口签名里出现"某个实现方"的包名** | 抽象失效：`SyncSource.Load` 返回 `*mockhis.Dataset`，导致业务包依赖 mock 包、"接真实 HIS 只需换实现"变成假话 | 契约放中立的 `internal/his`；**看到接口签名里有具体包名就该警觉** |
| 接口按"实现方"拆而不是按"谁用"拆 | 测试 fake 被迫实现用不到的方法 | `appointmentStore`（患者侧）与 `doctorAppointmentStore`（医生侧）分开声明，即使实现是同一个 repo |
| 为 4 行逻辑抽出新包 | 零语义的间接层 | 工具包平铺在 `internal/`；**抽包前先问"它有独立的语义边界吗"** |

细节：`AGENTS.md` §2.1/§2.2，`docs/MODULES.md` §7。

## 2. 并发与 context

| 易错点 | 症状 | 防法 |
|---|---|---|
| **复用已经 `cancel()` 的 context 做恢复** | 恢复路径永远返回 `context.Canceled`，**从未成功过一次**（H1） | 恢复/兜底分支**必须自己造 context**；`defer cancel()` 而非提前手动 cancel |
| singleflight 回源直接用调用方的 ctx | leader 被取消 → 所有健康跟随者一起收到 `Canceled` | 回源用 `context.WithoutCancel(ctx)` + 独立超时 |
| 后台 goroutine 里的 panic | handler 里是 500，**后台任务是整个进程没了** | 不可信输入的解析函数必须有 fuzz 目标 |
| `Stop()` 不幂等 | 回滚路径与 `main` 的 defer 都调用 → close 已关闭 channel 而 panic，**恰在最需要优雅退出时** | `sync.Once`；并在启动失败路径上测一遍 |
| 无界地起 goroutine | 单次同步打出数百请求被上游限流/封禁 | `errgroup.SetLimit`（spec §7.3 限并发 5） |

**判据**：任何"只在异常路径上执行"的代码，都要问一句"它拿到的 context 还活着吗"。

细节：`AGENTS.md` §2.3，`docs/MODULES.md` §6、`docs/FIXES.md` H1。

## 3. 数据一致性（Redis / MySQL）

### 号源（本项目最贵的一条防线）

| 易错点 | 症状 | 防法 |
|---|---|---|
| 预热用 `SET` 而非 `SETNX` | 把并发已扣减的号源"还回去" → **直接超卖** | 只用 `SETNX` |
| 键不存在返回 `0`（当"无余量"） | Redis 冷启动后**所有抢号全部失败**，且提示是"号源不足"，排查方向完全错 | 返回 `-1`（`StockNotLoaded`），调用方先预热再重试 |
| 回补不做容量上限 | 重复回补（补偿 + cron 同时命中）把余量推过总容量 → 超卖 | 钳位到 capacity |
| 回补时 `INCRBY` 创建了新键 | 凭空造出号源 | 键不存在直接返回 `-1` 跳过 |
| **钳位用裸 `SET`** | 清掉 TTL，号源键变永久；历史排班又不在对账扫描范围 → **错值再也不会被修正**（M1） | `SET ... KEEPTTL` |
| 对账用无条件 `SET` | 读 MySQL 与写 Redis 之间有时间窗，期间并发扣减会被覆盖回来 → **对账本身制造超卖** | `CompareAndSet`（比对更新），值变了就放弃 |

### 幂等与超时释放

| 易错点 | 症状 | 防法 |
|---|---|---|
| 失败清理用无条件 `DEL` | 删掉**已完成**的记录 → 后续重放查不到结果 → 幂等保护形同虚设 | Lua 比对删除（只在值仍是占位值时删） |
| `Complete` 用 `SET` 而非 `SET XX` | 键已过期时凭空创建，让一个已关闭的幂等窗口重新生效 | `SET ... XX` |
| 超时释放不带状态条件 | 多实例并发扫同一批订单 → **重复回补号源** | "带状态条件的 UPDATE"，用 `RowsAffected` 当闸门 |
| 幂等恢复时把**任何**错误当冲突 | 数据库抖动被报成"您已预约"（M2），底层错误既无包装也无日志 | 只有 `ErrNotFound` 是冲突，其余 `apperr.Wrap` |

细节：`AGENTS.md` §2.4，`docs/MODULES.md` §4，`docs/FIXES.md` M1/M2。

## 4. SQL 与 GORM

| 易错点 | 症状 | 防法 |
|---|---|---|
| **手写 JOIN 忘了软删除条件** | 已软删除的行照常出现在结果里（医生列表里出现已删医生） | GORM 的软删作用域**只在 `Model(&Struct{})` 时自动生效**；`Table("...")` 手写必须显式 `deleted_at IS NULL` |
| 列表接口用 OFFSET | 代价随页码线性增长（实测深页 **38×**） | 游标分页：`WHERE id < ?` + `ORDER BY id DESC` + `LIMIT limit+1` |
| 忘了 `limit+1` 探测行 | 无法判断 `has_more`，只能多查一次 COUNT | `limit+1`，多出的那行只用来置标志、不返回 |
| page size 不设上限 | 一次请求把整张表拉进内存（**最容易被利用的资源耗尽入口，且不需要任何权限**） | `model.NormalizePageSize` 夹在上限内；有 fuzz 目标守护 |
| 空切片返 `null` | 前端处理 `null` 与 `[]` 的路径不同 | `model.NonNil()` |
| 事务里做网络调用 | 事务被 Redis/LLM 的延迟拖长，锁持有时间不可控 | 事务内禁止网络调用（Redis 扣减在事务**之前**） |
| 列表 SELECT 列在文件里写两遍 | 改一处漏一处，两个接口字段对不上 | 抽常量（`syncLogSelect` / `doctorAppointmentSelect`） |

细节：`AGENTS.md` §2.5、§5.8，`docs/MODULES.md` §3。

## 5. 安全与鉴权

| 易错点 | 症状 | 防法 |
|---|---|---|
| **把路由层 RBAC 当成资源层授权** | 任何医生换个 ID 就能读他人数据（H2 候诊队列；此前还有预问诊报告）。**同一类漏洞出现过两次** | 凡是返回**未脱敏个人数据**的端点，都要问"它做了资源层归属校验吗"；发现一处就**把同类端点全扫一遍** |
| 授权检查写在"取数据"之后 | 虽然最终拒绝了，但数据已被读出（日志、内存、指标里可能留下） | **先鉴权、再查询**；集成测试断言"越权时响应体里不含任何业务字段" |
| 脱敏函数在短输入上原样返回 | 脱敏静默失效（M5：`IDCard` 长度 10 时 0 个星号） | 守卫条件的边界要算准（头 6 + 尾 4 ⇒ 至少 11 位才够）；**加 fuzz 守护"够长就必须屏蔽掉至少一个字符"** |
| 审计里存请求体 | 请求体含手机号、口令、病情描述 —— 等于把前面所有脱敏工作作废 | 审计只记元信息；`audit_logs` 刻意没有 payload 列 |
| 密钥进仓库 | 历史里可恢复（`.gitignore` 只防未来） | 仓库不含任何密钥；本地用 `cmd/genlocal` 生成；`config.Validate()` 按特征拒绝可预测密钥 |
| 登录失败不执行假比对 | 响应时间可枚举账号是否存在 | 失败路径也走一次同 cost 的 bcrypt 比对 |
| 限流器"从未被测试执行过" | 所有用例都在开头清限流键绕开它 → **一个静默失效的限流器没有任何症状** | 专门写用例真的去打满桶、断言 429 + `Retry-After` |

细节：`AGENTS.md` §2.6，`docs/MODULES.md` §4.4、§6.3、§6.7。

## 6. 写测试时的坑（**最高频**）

### 6.1 三种"看起来在断言，其实恒为真"

| 反模式 | 为什么测不出东西 | 正确写法 |
|---|---|---|
| `assert.Zero(t, fake.err == nil && fake.id == 0)` | fake **不会因为被调用而改变字段**，表达式与"分支是否走到"无关 | **数调用次数**：`assert.Zero(t, fake.calls)` |
| fake 方法忽略参数：`EnsureGroup(context.Context) error` | 放弃了"调用方传的 ctx 有效吗"的验证 —— H1 因此活了很久 | fake 至少检查一次实现会透传给下游的关键参数 |
| 断言 `resource == "admin"`（当时实现恰好这么返回） | **把错误行为写成期望值**，测试全绿而功能是错的 | 拿到一个"看起来对"的期望值时，**回代码确认它是不是真的对** |

### 6.2 fuzz 报失败时，先怀疑断言

首次跑 11 个 fuzz 目标报了 3 个失败，**只有 1 个是代码缺陷**，另 2 个是我的断言提了实现做不到的要求。

| 错误断言 | 反例 | 为什么错 |
|---|---|---|
| 要求 JSON 载荷字节级往返非法 UTF-8 | `"\xf5"` | JSON 字符串**无法承载非法 UTF-8**（会换成 U+FFFD） |
| 要求脱敏输出 ≠ 输入 | `"0***"` | 函数确实替换了后 3 位，只是原文尾部本来就是 `*` |
| 要求长度按 rune 守恒 | 18 位数字过 `Phone` | `Phone` 对超长输入会归一到 11 位，本就不守恒 |

> **流程：fuzz 红 → 回实现读一遍 → 问"这条性质真的必须成立吗" → 才决定改代码还是改断言。**
> 把 fuzz 当"红即改"，会把三处**正确**的行为改坏。

### 6.3 等待型断言

```go
// ✗ 等的是前置状态，断言的是最终状态 —— 约 40% 概率失败
for { if s.callCount() > 0 { break } ... }
assert.Equal(t, 1, q.ackCount())

// ✓ 等"你即将断言的那个状态"
require.Eventually(t, func() bool { return q.ackCount() > 0 }, 2*time.Second, 5*time.Millisecond)
```

**判据**：等待条件必须是**断言目标的本身**，不是它的前置状态。

### 6.4 其它

| 易错点 | 防法 |
|---|---|
| 关键测试**没有反向验证** | 写完后**故意改坏实现，确认用例变红**。没红就说明它没在断言 |
| 只跑一遍就说"不 flaky" | 要**在 CPU 负载下**跑（起几个后台忙循环）；单独跑很难触发 |
| 测试数据用绝对日期 | 过几天全部过期，症状是"莫名其妙抢不到号"；用相对值或固定常量 |
| 需要隔离的键不用用例名派生 | 用例之间通过共享状态互相干扰；幂等键还要注意**最小长度校验**（<8 字符会被参数校验拒掉） |
| 改测试夹具后只跑新用例 | **立刻跑全包** —— 曾把 map 形式的夹具"简化"成单值，一次弄坏两个既有用例 |

细节：`AGENTS.md` §5.9、§5.11、§5.12，`docs/HANDOVER.md` §2.7-C、§2.8。

## 7. 测试基建与 flaky

| 易错点 | 症状 | 防法 |
|---|---|---|
| **夹具用随机数保证唯一** | `UnixNano()%100000` 只有 10 万种取值，套件播种上百条 → 生日悖论下每 3~5 次撞一次（F2）。**报错的用例每次都不同**，极易被误诊为"那个用例不稳定" | 用**单调计数器**（`atomic.Uint64`）：唯一性从概率保证变成**构造性保证** |
| 用 `mysqladmin ping` 判断 MySQL 就绪 | `docker-entrypoint` 会先起临时 server，此时 ping 已成功 → 随机 `driver: bad connection` | 用**真实查询**探测，且连续两次成功 |
| 集成测试复用自己的临时装配 | 测的是"测试搭的东西"，真实启动路径（中间件顺序、依赖注入）仍没覆盖 | 复用 `app.Build()` 同一套装配，DDL 直接执行 `docs/schema.sql`（**顺带把 schema 也验证了**） |
| 基准没有基线就解读绝对值 | 把"本机 Docker 端口转发慢"误判成"Lua 慢" | **先测基线**（裸 `PING`）再解读 |

细节：`docs/FIXES.md` §6，`AGENTS.md` §5.1、§5.11。

## 8. 工具链与环境

| 易错点 | 症状 | 防法 |
|---|---|---|
| 以为 alpine 镜像自带 gcc | `-race` 报 cgo 不可用；`CGO_ENABLED=0` | 用 **Debian 变体**（`golang:1.27.1`）开箱即用，且比 alpine 快一倍多（alpine 的 `apk add` 无法缓存） |
| 容器内拉 Go module | 满屏 `dial tcp ... connection refused`，**看着像代码问题其实是网络** | 挂宿主机 `GOMODCACHE` + `GOPROXY=off` |
| Git Bash 改写容器内路径 | `-w /app` 被转成 `C:/Program Files/Git/app` | `MSYS_NO_PATHCONV=1` |
| 用 `@latest` 装静态检查工具 | CI 因上游发版而变红（不是你的代码坏了） | **钉版本** |
| `gofmt -w` 放进 CI | CI 里改文件毫无意义 | 用 `gofmt -l` + 非空则失败 |
| 升级 TS 大版本后不删 `node_modules` | npm 的 peer 变体是粘性的，会解析到旧变体，出现"看起来能用"的假象（**曾因此得出过错误结论**） | 升级大版本后**删掉重装**再下结论 |
| 前端升到 TS 7 | TS7 是 Go 重写版，不再提供 JS 编译器 API → `vue-tsc` 崩溃、`typescript-eslint` 直接抛错 | 锁 5.9.3 |

细节：`AGENTS.md` §5.2、§5.3、§5.10，`.github/workflows/ci.yml` 注释。

## 9. 文档与"事实来源"

| 易错点 | 症状 | 防法 |
|---|---|---|
| **手写路由清单** | 文档把管理端点写成 `/api/v1/audit-logs`（少了 `/admin/`），把已实现的端点列为待办 → **照文档调接口得 404，然后开始怀疑代码**。同类错误犯过两次 | 路由清单以 `router.go` 或 **gin 启动输出**为准；**能从代码导出的清单就不要手写** |
| 把"打算做"写成"已完成" | `database-review.md` 声称"service 会复活软删除行"，代码里没有任何 `Unscoped()`/`deleted_at = NULL` 调用 | 写文档前**回代码确认**；不确定就写"设计如此，尚未实现" |
| 注释与实现相反 | 注释说"跳过损坏条目"，代码是整体失败 | 与实现矛盾的注释比没有注释更糟；**改实现时顺手扫一眼相邻注释** |
| 报覆盖率不说口径 | `repository` 按包统计 6.4%、集成口径 67.5%，差 10 倍 → 曾经据此误判"数据访问层几乎没测" | 报数时**连口径一起报** |
| 拿新的测量覆盖旧的 | 分页 38× 与文档里 284× 量级不同（不同查询/口径） | 两个都保留并**写明测量条件**，不要用新数字抹掉旧的 |

细节：`AGENTS.md` §5.7，`docs/FIXES.md` §1。

## 10. 重复与抽象

| 易错点 | 症状 | 防法 |
|---|---|---|
| 同一段逻辑在多个 service 里各写一份 | `doctorIDOf` 三份实现（两份逐字节相同），改一处漏两处 | 收敛为包级函数（`resolveDoctorID`）；**错误码与文案必须一致** |
| 同一语义的条件写两遍 | `IsActive` 与内联条件各一份 → 加新状态时必漏改一处 | 抽出以状态字符串为参数的版本，两处共用 |
| 为"将来可能需要"保留旋钮 | `SyncDeps.Concurrency` 生产从不设、spec 也定死了值 | 删掉；**需要时再加比留着不用的好** |
| 保留无人使用的返回值 | `UpsertSchedule` 的 `created`、`UpsertDoctor` 的 ID 都被调用方丢弃 | 收窄签名 |
| 保留不可达的错误通道 | `runPhase` 的 errgroup 错误分支永远走不到（三个 upsert 都返回 nil），**读起来却像"失败会中止整批"** | 让代码形状匹配真实语义，并注释说明为什么不需要错误通道 |
| 留一个"以后填"的空字段 | `audit_logs.detail` 从没写过也没读过，而审计的设计前提正是"不存请求体" | **删列**。留空的 payload 字段只会诱使后人往里塞敏感数据 |
| 留一个"有列但从不写入"的字段 | `sync_logs.trace_id` 永远是 NULL | 二选一：**接上**（它符合项目"TraceID 贯通"的设计）或删掉；不要留着 |

**通用判据**：抽出/保留之前问一句 —— **"删掉它会怎样？"** 如果答案是"什么都不会发生"，就删。

细节：`docs/FIXES.md` §3。

## 11. 收尾动作（本项目的**主要**失效模式）

跨所有轮次的统计结论：

> **设计判断通常站得住，出问题的是收尾动作。**

历史上反复出现的形态：

1. **凑导入占位**（`var _ = strings.TrimSpace`，4 次）—— 写完不编译
2. **写了不跑**（占位文件当成已完成，3 次）
3. **注释声称有、实际没有**（指标、行为，2 次）
4. **测试看起来在断言、其实恒为真**（3 次）
5. **断言提了实现做不到的要求**（fuzz，3 次）

**这三条能挡住上面绝大多数：**

```
① 每写完一个文件立刻编译          —— 8 个自我引入的错误里 5 个会被这一步拦下
② 关键测试做反向验证              —— 唯一能证伪"测试在说谎"的方法
③ 等待型断言等最终状态            —— 挡掉时序竞争类的 flaky
```

细节：`docs/HANDOVER.md` §5.4、§5.5。
