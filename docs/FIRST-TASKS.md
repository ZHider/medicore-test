## 0. 动手前：三条规矩

这三条不是"建议"，是这个项目的硬规则。**违反它们会直接破坏项目。**

| 规矩 | 为什么 |
|---|---|
| **① 加任何依赖之前先问** | 加依赖这个动作**会出网**，走机主**计费**的代理；而且容器里拉不到新依赖。规范问法：「要什么 + 为什么现有依赖做不到」 |
| **② 不要为了前端方便去改后端契约** | 后端契约被 67 个集成测试和 268 个单元测试守着。真有需要，先确认，那会是一轮独立改动 |
| **③ 改完必须跑门槛** | `nub run lint`（静态检查）和 `nub run test`（测试）。**两个都要绿** |

**另外两个"专业习惯"**，从第一个任务就请养成：

- **关键逻辑要写测试，而且要反向验证** —— 故意把实现改坏，确认测试**真的变红**。
  一条永远不会失败的测试等于没有测试。
- **失败时先问"是我的期望错了吗"** —— 而不是立刻去改实现。
  本项目里相当一部分"测试失败"最后发现是**测试自己写错了**。

## 任务 1：给前端加一个纯函数 + 测试

| | |
|---|---|
| **目标** | 走一遍"写代码 → 写测试 → 跑门槛"的最短闭环 |
| **你会学到** | 纯函数、边界、**为了让测试稳定而设计参数** |
| **预计** | 30 分钟 |

### 要做什么

在 `frontend/src/utils/datetime.ts` 里加一个函数：把
`"2026-09-13 14:05:00"` 这种时间转成人类友好的相对时间。

```ts
// 期望行为
relativeTime('2026-09-13 14:05:00', new Date('2026-09-13 14:05:10'))  // → '刚刚'
relativeTime('2026-09-13 14:05:00', new Date('2026-09-13 14:08:00'))  // → '3 分钟前'
relativeTime('2026-09-13 14:05:00', new Date('2026-09-13 16:05:00'))  // → '2 小时前'
relativeTime('2026-09-13 14:05:00', new Date('2026-09-16 14:05:00'))  // → '3 天前'
relativeTime('2026-06-01 10:00:00', new Date('2026-09-13 14:05:00'))  // → '2026-06-01'（太久就显示日期）
```

### ⚠️ 关键设计点（**这是本任务真正的考点**）

函数签名必须是：

```ts
export function relativeTime(value: string, now: Date = new Date()): string
```

**为什么要把 `now` 做成参数？** 因为如果函数内部直接调 `new Date()`，
测试就只能"猜当前时间"，结果**随机器时区、随运行时刻变化** ——
这类测试会偶发失败，最后所有人都学会"重跑一下就好"，**整个测试套件的可信度就归零了**。

把 `now` 传进来，测试就**完全确定**。这条规矩写在本项目 `frontend/AGENTS.md` §5.8：
> 断言基于字段值，不要基于绝对时间戳。

### 要动的文件

| 文件 | 做什么 |
|---|---|
| `frontend/src/utils/datetime.ts` | 加函数（注意：要先看这个文件已有的时间解析工具，**复用**它） |
| `frontend/src/utils/datetime.spec.ts` | 加测试（这个文件已存在，照它的风格写） |

### ✅ 验收标准

- [ ] 上面 5 个例子全部通过
- [ ] 至少覆盖这些边界：**刚好 60 秒**、**未来时间**、**非法输入**
- [ ] `nub run frontend:test` 全绿（不只是你的新用例）
- [ ] `nub run frontend:lint` 与 `nub run frontend:typecheck` 通过
- [ ] **反向验证**：把实现里的 `Math.floor` 改成 `Math.round`（或改掉某个边界），
      确认**至少有一条用例变红**，然后改回来

### 卡住了看哪

- `frontend/src/utils/datetime.ts` 里已有的 `parseApiTime` —— **先复用它**，别重复造
- `frontend/AGENTS.md` §5.8（测试三条规矩）
- 边界值怎么定？看 `datetime.spec.ts` 里现有的写法

## 任务 2：给后端补一个 service 单元测试，并反向验证

| | |
|---|---|
| **目标** | 学会这个项目"不依赖数据库也能测业务"的写法 |
| **你会学到** | 接口由使用方定义、内存 fake、反向验证 |
| **预计** | 45 分钟 |

### 背景

这个项目的 `service` 层**不直接依赖 MySQL**，而是依赖一个**小接口**。
测试时注入一个"假的数据源"（fake），所以 268 个单元测试能在几秒内跑完。

看一下模板文件：**`backend/internal/service/audit_test.go`**
（它有 `fakeAuditStore`、表格驱动用例、以及"参数非法时不应发起查询"这种断言）

### 要做什么

给**一个目前测试覆盖薄弱**的 service 方法补测试。先自己找出候选：

```powershell
# 方式一：看哪些 service 文件还没有同名的 _test.go
cd backend
Get-ChildItem internal/service -Filter '*.go' | Where-Object { $_.Name -notmatch '_test' } | Select-Object Name
Get-ChildItem internal/service -Filter '*_test.go' | Select-Object Name

# 方式二（更靠谱）：从覆盖率里挑函数，而不是从文件列表挑
go test ./internal/service/... -coverprofile=$env:TEMP\svc.out
go tool cover -func=$env:TEMP\svc.out | Select-String -NotMatch '100.0%'
```

> **建议**：挑一个 `0.0%` 且**有分支逻辑**的方法（有 if/else、有错误返回的）。
> 注意：`internal/service/` 下大部分文件**已经有测试**了，
> 所以方式二（按覆盖率挑函数）通常比方式一（按文件配没有测试）更能找到目标；
> `deps.go` 只是接口声明、`health.go` 几乎没有分支，都不适合。**自己找一个真正值得测的。**

### ✅ 验收标准

- [ ] 新测试**不连接数据库**（`go test ./internal/service/...` 不带任何环境变量就能跑通）
- [ ] 至少覆盖：**正常路径** + **至少一个错误/边界路径**
- [ ] 断言写的是**"哪个分支被走到了"**，不是夹具里的静态值。
      ⚠️ 反例（这种写法**恒为真，测不出东西**）：
      ```go
      assert.Zero(t, fake.err == nil && fake.id == 0)   // ❌
      ```
      正解是**数调用次数**：`assert.Zero(t, fake.calls)` —— 这样"该分支没被走到"才测得出来
- [ ] **反向验证**：改坏被测实现，确认你的测试变红，然后改回
- [ ] `nub run backend:test` 与 `nub run lint` 全绿

### 卡住了看哪

- **`backend/internal/service/audit_test.go`**（照抄它的结构）
- `backend/internal/service/deps.go` —— 看 service 依赖了哪些小接口
- `docs/PITFALLS.md` §6.1「三种看起来在断言，其实恒为真」（★ 必读）

## 任务 3：补上一个已记录的真实缺口（errcode 守护测试）

| | |
|---|---|
| **目标** | 修掉 `docs/FIXES.md` 里记的 **N1** —— 一个**真实待办**，不是练习题 |
| **你会学到** | 读缺陷清单 → 动手补 → 反向验证 |
| **预计** | 45 分钟 |

### 背景（先自己读一遍 `docs/FIXES.md` 里的 N1）

`backend/internal/errcode/errcode.go` 里有**一套常量 + 两张 map**：

```go
const ( ErrInvalidParam Code = 40001; ... )   // ① 常量
var messages  = map[Code]string{ ... }        // ② 文案
var httpStatus = map[Code]int{ ... }          // ③ HTTP 状态码
```

代码注释写着"必须同步改"，但**这个包没有任何测试** —— 全靠人记。
漏改的后果：某个错误码会落到"未知错误 / 500"，而**不会有任何报错**。

### ⚠️ 先发现一件事（本任务的隐藏考点）

`docs/FIXES.md` 的 N1 建议是「遍历三张表的 key 集合断言三者相等」。

**但你动手时会发现：`const` 块在运行时是枚举不出来的。**
所以"三张表"这个说法**照做不了**。

> **这正好是本项目的一条核心规矩**：文档可能错，**代码不会**。
> 遇到文档和代码不一致，**信代码**，并且顺手把文档改对。
> （本项目的手写路由清单已经错过两次，`AGENTS.md` §5.7 专门记了这件事。）

### 要做什么

**基本版**（必做，约 20 行）：断言两张 map 的 **key 集合完全相同**。
这能抓住最常见的错法 —— 加了常量、也加了文案，但**忘了加 HTTP 状态码**。

**进阶版**（可选，用来堵住"两张 map 都忘了"）：用 Go 标准库 `go/parser`
解析 `errcode.go` 源码，取出 `const` 块里所有 `Code` 常量，
断言它们**都出现在两张 map 里**。

### ✅ 验收标准

- [ ] 新建 `backend/internal/errcode/errcode_test.go`
- [ ] **反向验证（必须做）**：从 `httpStatus` 里删掉任意一项 → 测试**必须变红**
      → 然后改回来。（做不到这一步，说明你的测试没在起作用）
- [ ] `go test ./internal/errcode/...` 通过
- [ ] 顺手把 `docs/FIXES.md` 里 N1 那条**移到"已修"**，并更新前面的缺陷计数
- [ ] `nub run backend:test` 与 `nub run lint` 全绿

### 卡住了看哪

- `docs/FIXES.md` 的 N1 原文
- 任何现有 Go 测试文件（比如 `internal/model/pagination_fuzz_test.go`，很短，适合入门）

## 任务 4：给已有接口加一个**可选**查询参数（前后端贯通）

| | |
|---|---|
| **目标** | 走一遍完整的前后端贯通改动：后端三层 + 前端筛选框 + 测试 |
| **你会学到** | 分层的实际手感、为什么"可选参数"是安全的、"契约变更"要走什么流程 |
| **预计** | 1.5 小时 |

### 要做什么

给 `GET /api/v1/admin/audit-logs` **加一个可选的 `role` 过滤参数**
（按角色筛审计日志：patient / doctor / admin）。

这个接口**已经支持** `resource` / `action` / `trace_id` / `from` / `to` / `user_id`，
你要做的是**照着现有参数的写法**再加一个。

### ⚠️ 真实工作里的流程（**先做这一步，别跳**）

加查询参数属于**接口契约变更**。项目规矩是：**先确认再动手**。

练习时把它当成"已经确认过的需求"，但**请在你的提交信息里写明这是一次契约变更**。
真实的团队里，这一步是发消息问、或者开个 issue —— 而**不是自己悄悄改掉**。

### 要动的地方（按依赖顺序）

| 层 | 文件 | 做什么 |
|---|---|---|
| 1 | `backend/internal/handler/audit.go` | 从 query 里读 `role` |
| 2 | `backend/internal/service/audit.go` | 加进 `AuditQuery`，**在这里做格式校验** |
| 3 | `backend/internal/repository/audit.go` | 加进 `AuditFilter`，加一个 `WHERE` |
| 4 | `backend/internal/service/audit_test.go` | 加单元测试（照 `TestAuditList_PassesFiltersThrough` 写） |
| 5 | `backend/test/integration/` | 加集成测试（照 `trace_test.go` 写） |
| 6 | `frontend/src/types/api.ts` | `AuditLogQuery` 加字段 |
| 7 | `frontend/src/views/admin/AuditLogsView.vue` | 加一个筛选输入框 |
| 8 | 文档 | 更新 `frontend/AGENTS.md` §3.7 的参数列表 |

### 🔑 一个必须想清楚的设计决定

`trace_id` 格式非法时返回 **40001**，而 `user_id` 非法时是**静默忽略**。
**你加的 `role` 该学哪个？**

提示：想一下"静默忽略"的用户体验 —— 管理员选了"医生"这个角色，
但参数拼错了，后端不报错、也不过滤，返回**全部日志**。
管理员会以为"医生相关的日志居然这么多"。

**先自己想，再去看 `frontend/AGENTS.md` §3.7 里那张对比表。**

- [ ] 传合法 `role` 时只返回该角色的日志
- [ ] 传非法 `role` 时返回 `40001`（按你上面的决定）
- [ ] 后端单元测试 + 集成测试都覆盖了这三种情况

- [ ] `nub run test` 全绿、`nub run lint` 全绿

**逐条对一遍：**

| 检查项 | 为什么 |
|---|---|
| [ ] `nub run lint` 绿（含 `frontend:typecheck`） | 类型错误会让构建中断 |

| [ ] **关键改动做过反向验证** | 改坏实现 → 确认变红 → 改回。这是本项目最看重的习惯 |
| [ ] 没有新增依赖 | 有的话先问 |

| [ ] 新增/修改了接口 → 更新了对应文档 | 文档承诺了不存在的功能，比没文档更糟 |

```

<为什么改。如果修的是缺陷，写清根因；如果是新功能，写清要解决什么问题。>
```

类型用 `feat` / `fix` / `docs` / `chore` / `perf` / `refactor`。
