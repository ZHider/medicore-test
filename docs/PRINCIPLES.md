# 为什么这样设计 —— 设计原则与最佳实践

> **给初级的同事。** 这份文档不讲"这个项目怎么做的"（那是 `ONBOARDING.md`），
> 而是讲**"为什么这样做是对的"**，以及**"我怎么知道自己正在做错"**。
>
> 里面的每条原则都配了本项目里的**真实代码**当例子。
> 原则是**可迁移的** —— 你换个项目、换个语言，它们照样成立。

## 0. 怎么用这份文档

| | |
|---|---|
| **别一次读完** | 一共 9 章，每章 5 分钟。**一天读一章**比一次读完有用 |

## 1. 分层：每一层只做自己的事

### 原则

> **代码的依赖方向只能单向流动。每一层只做自己那一件事，而且知道得越少越好。**

本项目的流向：

```
handler → service → repository → model
（处理 HTTP）（业务规则）（数据访问）（数据结构）
```

**为什么？** 不是为了"看起来专业"，而是为了三个很实际的好处：

| 好处 | 具体表现 |
|---|---|
| **能单独测试** | service 不认识 HTTP，也不认识 MySQL，所以测试时喂假数据就行。本项目 268 个后端测试**几秒跑完**，不用起数据库 |
| **换东西不用改业务** | 哪天换数据库，只改 repository 一层 |
| **不容易写错权限** | 权限校验有**固定位置**，不会散落在十个文件里 |

### ❌ 反例：业务逻辑写在 handler 里

```go
// 反例：看起来能跑，但后患无穷
func GrabAppointment(c *gin.Context) {
    var req GrabRequest
    c.ShouldBindJSON(&req)

    // ❌ handler 直接操作数据库
    var sched Schedule
    db.First(&sched, req.ScheduleID)
    if sched.Remaining <= 0 {
        c.JSON(409, "no stock")
        return
    }
    sched.Remaining--
    db.Save(&sched)
    db.Create(&Appointment{...})
    db.Redis.Decr("stock:" + req.ScheduleID)   // ❌ 缓存逻辑也在里面
    c.JSON(200, "ok")
}
```

**这段代码有四个问题，每一个都会在某天咬你：**

1. **没法测试** —— 要跑它必须起 MySQL + Redis，测试变得又慢又脆
2. **没有事务** —— 中间任何一步失败（比如 `db.Create` 挂了），号已经扣了但预约没建，
   **数据不一致，而且没人知道**
3. **权限没写** —— 这段代码里根本没有"这个排班能不能被这个用户抢"的判断
4. **逻辑不可复用** —— 将来异步接口、管理后台也要抢号时，只能复制粘贴

### ✅ 正例：本项目的分层

| 层 | 文件 | 只做什么 |
|---|---|---|
| handler | `internal/handler/appointment.go` | 把 JSON 解析成结构体、校验格式、调 service、返回响应 |
| **service** | `internal/service/appointment.go` | 幂等检查 → 扣号源 → **数据库事务** → 失败回补 Redis |
| repository | `internal/repository/appointment.go` | 执行 SQL，把 `gorm.ErrRecordNotFound` 翻译成 `ErrNotFound` |
| model | `internal/model/appointment.go` | 定义结构体与状态常量 |

**检验方法（很灵的）**：问自己一句 ——
**"如果我把 HTTP 换成 gRPC/命令行，这层代码要改吗？"**
- service 要改 → ❌ 它偷偷依赖了 HTTP
- service 不用改 → ✅ 分层是对的

### 🔍 怎么发现自己违反了

| 症状 | 说明 |
|---|---|
| 你想测一段业务逻辑，但必须先起数据库 | 业务和数据访问混在一起了 |
| 同一个业务规则在两个地方各写了一遍 | 它**没有家** —— 迟早会不一致 |
| 改一个小需求要动三四个文件 | 分层没切干净 |
| 一个函数很长、做很多事 | 通常意味着它跨了层 |

> **本项目自查命令**（建议你提交前跑一次）：
> ```bash
> # handler 里不该出现 GORM
> grep -rn "gorm.io/gorm" backend/internal/handler
> # service 里不该出现 gin.Context
> grep -rn "gin.Context" backend/internal/service
> ```
> **两条都应该是空的输出。**

### ⚖️ 什么时候可以打破

- **极小的只读接口**（比如"返回系统版本号"）不值得为它建三层，直接写在 handler 里没问题
- **但只要有业务规则或写操作，就必须分层** —— 区别在于"有没有规则"，不在于"代码多少行"

## 2. 边界：谁不可信，校验放哪

### 原则一：**外部输入一律不可信，必须在信任边界上校验**

> **"信任边界"** = 数据从"不可信的地方"进入"你的系统"的那条线。
> 跨过这条线之前，一切都要检查。

浏览器传来的东西**全都不可信**：URL 参数、请求体、请求头、连 cookie 也是。

### ✅ 正例：本项目的信任边界（真实代码，注释有删节）

`backend/internal/traceid/traceid.go`（**下面是原注释的删节，不是逐字原文**）：

```go
// IsValid 判断 s 是否是本服务认可的 trace_id 形式：恰好 32 位十六进制。
//
// 这个判断是**信任边界**，必须严格，有两个各自独立的理由：
//   1. 目标列是 CHAR(32)。超过 32 字符时 MySQL 严格模式会拒绝整条语句，
//      而审计是**批量**写入的 —— 一条坏记录会让整批（100 条）一起失败。
//   2. 列排序规则是 ascii_bin（逐字节比较），大小写不同就是两个不同的值。
func IsValid(s string) bool { ... }
```

> **想看逐字原文就打开那个文件** —— 这也是本文档第 7 章要讲的：
> **摘要可以帮你理解，但代码才是权威。**

**这里发生过什么？** 请求头 `X-Trace-Id` 是**客户端可以随便设的**，
而它会被原样写进数据库。攻击者只要发一个**超长**的追踪号，
就能让包含它的**整批 100 条审计记录**一起插入失败 —— **一条请求抹掉一批审计**。

**教训**：`X-Trace-Id` 看起来只是个"追踪用的字符串"，不是"业务数据"，
所以当初没人觉得需要校验。**但"不可信"跟"重不重要"无关** ——
只要它来自外部、又要进你的存储，就必须过校验。

### ❌ 反例：相信外部输入的长度

```go
// 反例
id := c.GetHeader("X-Trace-Id")   // 长度？内容？完全没管
db.Create(&AuditLog{TraceID: id}) // 数据库列只有 32 字符 → 直接炸
```

### 原则二：**前端校验是体验，后端校验是安全**

> 前端校验**永远不能替代**后端校验。

**为什么？** 因为用户可以绕过前端：用 Postman 直接打你的接口、
在浏览器控制台改 JS、甚至自己写个脚本。

**正确的分工**：

| 位置 | 目的 | 做不做都一样吗 |
|---|---|---|
| **前端**校验 | **体验** —— 立刻告诉用户"手机号要 11 位"，不用等一次网络往返 | 可以绕过，但值得做 |
| **后端**校验 | **安全** —— 真正决定数据能不能入库 | **必须做，而且要做全** |

**本项目怎么做的**：前端注册页会即时校验手机号格式，
但后端**也**会校验一遍（不满足返回 `40001`）。**两边都写，不是重复劳动。**

### 原则三：**角色够 ≠ 这是你的东西**

这一条特别容易搞错，本项目的两个真实缺陷都出在这里。

**要分清两种权限检查**：

| 检查 | 回答的问题 | 失败返回 |
|---|---|---|
| **角色检查（RBAC）** | 你是**医生**吗？ | `40301` |
| **归属检查** | 这个预约是**你的**患者吗？ | `40302` |

**❌ 常见错误**：只在路由上挂了"必须是医生"，就以为安全了。

```go
// 反例：路由层只检查了角色
admin := r.Group("/", middleware.RequireRole(RoleDoctor))
admin.GET("/schedules/:id/queue", h.Queue)   // ❌ 任何医生传任意排班 ID 都能查！
```

**后果**：任何医生换个排班 ID，就能拿到**别的医生**患者的姓名和 user_id
（而这个接口刻意不脱敏）。**这是一次真实发生过的信息泄露。**

**✅ 正例**：在 service 层再判一次"这是不是你的"

`backend/internal/service/access.go` 的真实代码：

```go
// resolveDoctorID 由用户 ID 解析医生档案 ID。
//
// appointments / medical_records / ai_pre_reports 三张表存的都是 doctors.id，
// 直接拿 users.id 比较会**永远不相等**，所以这一步躲不掉。
func resolveDoctorID(ctx context.Context, doctors doctorLookup, userID uint64) (uint64, error) {
    doctorID, err := doctors.FindIDByUserID(ctx, userID)
    if errors.Is(err, repository.ErrNotFound) {
        return 0, apperr.New(errcode.ErrForbidden, "当前账号没有医生档案")
    }
    ...
}
```

**注意注释里那句"直接拿 users.id 比较会永远不相等"** ——
这是个非常隐蔽的坑：`users` 表和 `doctors` 表是不同 ID。
如果不查这一步，归属校验会**永远失败**（或永远成功），而代码看起来完全正常。

### 🔍 怎么发现自己违反了

| 症状 | 说明 |
|---|---|
| 一个返回**别人数据**的接口，你只看到 `RequireRole` | **几乎肯定漏了归属校验** |
| 接口返回的字段里有患者姓名/手机号，但没查"是不是你的患者" | 同上 |
| 前端做了校验，后端没做 | 可以被 Postman 绕过 |
| `if id == otherId` 直接用，没确认两张表的 ID 是同一个东西 | 见上面那个 `users.id` vs `doctors.id` 的坑 |

> **本项目的规矩（值得学）**：发现一处这类问题时，
> **立刻把所有"返回他人数据"的接口扫一遍** —— 因为同一个根因通常不止一处。
> 本项目就是这样连着抓到两处（报告、候诊队列）。

### ⚖️ 什么时候可以打破

- **公开数据**不需要归属校验（比如科室列表、医生列表）
- **但**只要数据能指向"某个人"，就要问一句"凭什么他能看"

## 3. 数据：事实来源、约束、缓存

### 原则一：**事实来源只能有一个**

> 同一份数据存在多处时，**必须明确"以谁为准"**，并且写下来。

**本项目的例子**：号源（剩余号数）同时存在于 MySQL 和 Redis。

| | MySQL | Redis |
|---|---|---|
| 角色 | **唯一事实来源** | 加速 + 原子闸门 |
| 为什么需要 | 数据不能丢、要能恢复 | 高并发扣减必须快且原子 |

**规则**：两者不一致时**以 MySQL 为准**，每 5 分钟有个定时任务把 Redis 校准回去。

**❌ 如果没有"事实来源"这个概念会怎样？**
两处数据不一致时，**你不知道该信谁**，于是只能到处加"特殊处理"，
代码越来越乱，最后没人敢改。

### 原则二：**能用数据库约束保证的，不要用代码检查**

**❌ 反例（这是最经典的 bug 之一）**：

```go
// "先查再插" —— 两个请求同时到，就炸了
if !db.Where("appointment_id = ?", id).First(&Record{}).RecordNotFound() {
    return errors.New("病历已存在")
}
db.Create(&Record{AppointmentID: id})   // 两个并发请求会双双通过上面的检查！
```

这叫 **check-then-act**（先检查，再动手）—— 检查和动手之间**有时间窗口**，
另一个请求可以在这窗口里做完同样的事。

**✅ 正例**：让**数据库**来保证。

本项目的 `docs/schema.sql`：

```sql
-- medical_records 表
UNIQUE KEY uk_appointment (appointment_id) COMMENT '一次就诊一份病历'
```

有了这个唯一索引，第二个并发请求会被数据库**直接拒绝**。
你再把那个错误翻译成 `40004`（状态冲突）返回给用户就行。

**记住这句话**：**唯一性、非空、外键这类"数据本身必须成立的事"，
交给数据库；业务规则交给 service。**

### 原则三：手写 SQL 时要显式处理"软删除"

**背景**：本项目用**软删除** —— 删除不是真的删，而是把 `deleted_at` 设成时间。
查询时只返回 `deleted_at IS NULL` 的行。

**坑在哪**：ORM（GORM）会**自动**加上这个条件 —— **但只在你用它的"模型查询"时**。
一旦你手写 JOIN，它就**完全不介入**，已删除的行会照常出现。

```go
// ✅ 自动带上 deleted_at IS NULL
db.Model(&model.Schedule{}).Where(...)

// ❌ 必须自己写！否则查得到已删除的行
db.Table("doctors AS d").Joins(...).Where("d.deleted_at IS NULL AND u.deleted_at IS NULL")
```

**症状**：接口返回了"已经删掉"的数据，但测试全绿（因为测试数据没删过）。

### 原则四：**NULL 不是 0，也不是空字符串**

```sql
-- ❌ 语义错，但"碰巧"结果对
LEFT JOIN medical_records mr ... WHERE mr.id = 0

-- ✅ 正确
LEFT JOIN medical_records mr ... WHERE mr.id IS NOT NULL
```

**为什么 `= 0` 是错的？** JOIN 没匹配上时 `mr.id` 是 `NULL`，
而 `NULL = 0` 的结果是 `NULL`（既不是真也不是假），
转成布尔会得到 `false` —— **结果碰巧对，但语义完全错**。
换个判定列（比如判一个可能真为 0 的字段）就会出错。

### 🔍 怎么发现自己违反了

| 症状 | 说明 |
|---|---|
| 同一份数据在两个地方都能改，且没有"以谁为准"的说明 | 迟早不一致 |
| 代码里写 `if 已存在 then 报错`，然后才插入 | check-then-act，有竞态 → 改用唯一索引 |
| 手写了 `Table(...)`/`JOIN` | **检查有没有带 `deleted_at IS NULL`** |
| 用 `= 0` 或 `= ''` 判断 JOIN 是否有结果 | 应该用 `IS NULL` / `IS NOT NULL` |

### ⚖️ 什么时候可以打破

- **缓存不是必须的**。先用数据库跑通、量出性能问题**再**加缓存，
  而不是一开始就加（缓存会带来"不一致"这一整类新问题）
- **但**只要加了缓存，就必须同时决定**什么时候失效、以谁为准**

## 4. 并发：先检查再动手是原罪

### 原则：**"检查"和"动手"必须是同一个原子操作**

上面提过一次 check-then-act，这里单独成章，因为它是**并发 bug 的头号来源**。

### ✅ 正例一：用 `SETNX` 而不是 `SET`

`SETNX` = "SET if Not eXists"（不存在才设置）。它**判断和写入是一步完成的**。

本项目的号源预热就靠它。为什么不能用 `SET`？注释里写得很清楚：

```lua
-- backend/internal/repository/stock.go（真实注释）
-- 必须 KEEPTTL：裸 SET 会清掉 EnsureLoaded 用 SETNX 设置的过期时间，
-- 号源键就此变成永不过期的键，而 SETNX 也不会再刷新它。
-- 对历史排班而言更糟 —— 这个被永久钉住的错值再也不会被对账修正。
redis.call('SET', key, cap, 'KEEPTTL')
```

**读懂这段注释值得花几分钟**，它示范了什么叫"注释解释为什么"：
不是说"这里设置成 cap"，而是说"**不写 KEEPTTL 会发生什么**"。

### ✅ 正例二：返回三态，而不是布尔值

`backend/internal/repository/idempotency.go`（真实代码）：

```go
// Acquire 尝试占用幂等键。
//
// 返回 (是否本次占用, 已存在的预约ID, 错误)：
//   - (true, 0, nil)            首次请求，可以继续处理
//   - (false, id, nil)          该键已完成，id 为上次创建的预约
//   - (false, 0, ErrInFlight)   同一键的请求正在处理中
func (r *IdempotencyRepo) Acquire(ctx context.Context, userID uint64, key string) (bool, uint64, error) {
```

**为什么不用简单的 `bool`？** 因为调用方需要区分三种情况：

| 情况 | 该怎么处理 |
|---|---|
| 首次 | 正常走业务流程 |
| 已完成 | **直接把上次的结果返回**（这就是幂等） |
| 处理中 | 告诉用户"请稍候"，**不要重复执行** |

**如果一个函数返回 `bool`，"已完成"和"处理中"就没法区分** ——
你会把"正在处理"当成"已经做完"返回一个空结果给用户。

### ✅ 正例三：删之前先比对（compare-and-delete）

```lua
-- backend/internal/repository/idempotency.go（真实代码）
-- 比对删除保证只清理仍然处于处理中的键。
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

**为什么不能直接 `DEL`？** 因为可能发生这种事：

```
请求 A 处理失败 → 准备释放幂等键
                     ↓（这中间，另一个请求已经用同一个键成功了）
请求 B 成功       → 键里记的是"成功 + 预约 id=42"
请求 A DEL 键     → ❌ 把 B 的成功记录删了 → 用户再重试会重复占号
```

**比对删除**（"只有在还是我设的那个值时，我才删"）解决了这个问题。

### 🔍 怎么发现自己违反了

| 症状 | 说明 |
|---|---|
| 代码里有 `先查...然后...写`，而且可能被并发调用 | check-then-act |
| 用一个 `bool` 表示多状态 | 迟早要加第二个返回值 |
| 直接 `DEL` / `UPDATE` 一个可能有别人改过的值 | 可能需要 compare-and-set |
| "这个函数有并发问题吗？" —— **答不上来** | 那就是有 |

### ⚖️ 什么时候可以打破

- **单用户的、不可能并发的操作**不用想这些（比如用户改自己的昵称）
- **但只要涉及"共享的有限资源"**（号源、库存、余额、唯一名字），就必须想

## 5. 错误处理与可观测性

### 原则一：**区分"业务错误"和"系统错误"**

| 类型 | 例子 | 该给用户看什么 | HTTP |
|---|---|---|---|
| **业务错误** | 号源不足、参数不对 | **具体原因** | 4xx |
| **系统错误** | 数据库连不上、代码 panic | **"服务器内部错误"+ 追踪号** | 5xx |

**为什么不能都一样？**
- 业务错误对用户**有用**："号源不足"告诉他可以换一个排班
- 系统错误对用户**没用**，而且把技术细节暴露出去**有安全风险**
  （比如数据库表名、SQL 片段，等于给攻击者送情报）

**❌ 反例**：
```go
return err.Error()   // ❌ 可能把 "Error 1062: Duplicate entry 'IT57000' for key 'uk_code'" 直接回给用户
```

**✅ 正例**：包装成业务错误，原始错误只进日志
```go
apperr.Wrap(errcode.ErrInternal, "查询医生档案失败", err)
// 用户看到："服务器内部错误（追踪号 3f2a…）"
// 日志里有：完整的技术原因
```

### 原则二：**每个请求都要有追踪号**

**为什么？** 用户说"我点提交报错了"，没有追踪号你**什么都查不到** ——
日志里成千上万条，你不知道是哪一条。

**本项目的做法**：每个请求分配一个 32 位十六进制追踪号，
它同时出现在三个地方：

```
① 响应头 X-Trace-Id        → 前端能拿到
② 响应体 trace_id          → 前端显示在错误提示里
③ audit_logs.trace_id      → 数据库里能查
```

于是流程变成：**用户截图 → 你看到追踪号 → 一条 SQL 定位到那一次请求。**

> **注意那个"（追踪号 xxx）"**：本项目把它拼进了每个错误提示。
> 这么做的理由很实际 —— **让用户能自助提供排障信息**，
> 而不是只会说"它坏了"。

### 原则三：**用户报的错，不要撒谎**

**❌ 反例**（本项目真实避开的坑）：
登录被限流时提示"密码错误"。

**后果**：用户会去**改密码** —— 越改越触发限流，越锁越死。
而真正的原因是"你试太快了，等 12 秒"。

**✅ 正例**：
```go
if err.code === ErrorCode.RateLimited {
    // 限流时绝不能提示"密码错误"——用户会去改密码，越改越锁
    startWait(err.retryAfter ?? 60)
    return
}
```

**这条原则可以推广**：**错误提示必须指向正确的解决动作。**
提示"密码错误"但实际是限流 → 用户做了错误的动作 → 问题更严重。

### 🔍 怎么发现自己违反了

| 症状 | 说明 |
|---|---|
| 直接把 `err.Error()` 返回给用户 | 可能泄漏内部细节 |
| 接口报错时用户只能提供"它坏了" | 缺追踪号 |
| 错误提示让用户去做**错误的事** | 比如限流提示密码错误 |
| 日志里没有足够的上下文 | 你没法复现问题 |

### ⚖️ 什么时候可以打破

- 内部工具、给自己的调试接口，暴露细节反而方便
- **但**只要接口对最终用户开放，就要按上面来

## 6. 测试：一条不会失败的测试等于没有测试

这是本项目最看重的一章。**建议逐字读。**

### 原则一：**写完关键测试，要故意把实现改坏，确认测试真的变红**

这叫**反向验证**。

**为什么必须做？** 因为**写一条永远不会失败的测试是很容易的** ——
而且它比"没有测试"更危险：**它会给你虚假的安全感。**

**真实例子**（本项目踩过）：

```go
// 有人写了这条测试，然后它一直通过 —— 无论实现对不对
assert.Zero(t, fake.err == nil && fake.id == 0)
```

**为什么恒为真？** 因为 `fake` 是个**假对象**，
它**不会因为被调用而改变自己的字段**。
所以这个表达式跟"那段代码有没有被执行"**完全无关**。

**✅ 正确写法：数调用次数**

```go
assert.Zero(t, fake.calls)   // "这个分支不该被走到" → 那它就不该被调用过
```

### 原则二：**断言"没发生什么"时，要数次数**

延续上一条。"这个分支不该走到"这类断言，
**唯一可靠的写法是"检查那个分支的副作用没有发生"** ——
而最容易检查的副作用就是**调用次数**。

### 原则三：**测试必须是确定的**

**❌ 反例**：
```ts
// 函数内部调 new Date()，测试只能"猜"当前时间
expect(relativeTime('2026-09-13 14:05:00')).toBe('3 分钟前')  // 跑的时候不是 3 分钟前 → 随机失败
```

**✅ 正例**：把"现在"做成参数
```ts
export function relativeTime(value: string, now: Date = new Date()): string
// 测试里传一个固定时间 → 结果完全确定
relativeTime('2026-09-13 14:05:00', new Date('2026-09-13 14:08:00'))  // 永远等于 '3 分钟前'
```

**为什么这条特别重要？**
不确定的测试会**偶发失败**。偶发失败几次之后，大家就学会了
**"重跑一下就好"** —— 而这时**整套测试的可信度就归零了**：
真的出了 bug，也会被当成"又抽风了"。

**同类问题**：测试依赖机器时区（CI 是 UTC，你的电脑是东八区）、
依赖执行顺序、依赖网络。

### 原则四：**等待的时候，要等你即将断言的那个状态**

**❌ 反例**（本项目抓到一个约 40% 概率失败的用例）：
```go
// 等的是"业务逻辑被调用了"
for { if s.callCount() > 0 { break } }
// 断言的却是"确认已完成" —— 而完成发生在调用之后
assert.Equal(t, 1, q.ackCount())   // 有时是 0 → 偶发失败
```

**✅ 正例**：
```go
require.Eventually(func() bool { return q.ackCount() > 0 }, ...)  // 等"你要断言的那个状态"
```

**一句话**：**等待条件不能比断言"落后一步"。**

### 原则五：**测试失败时，第一件事是问"是不是我的期望错了"**

本项目里**相当一部分"测试失败"最后发现是测试自己写错了**。真实例子：

- 跑 fuzz 时 3 个失败，只有 1 个是代码缺陷，**另外 2 个是断言提了实现做不到的要求**
- 写测试时把"消息总数"写成了"患者发言数"
- 用 `toThrow` 去断言一个**返回 Promise 的函数**（它根本不 throw）

**所以正确的顺序是**：
```
测试失败
   ↓
先回实现读一遍，问"这个性质真的必须成立吗？"
   ↓
确认是代码错 → 改代码
确认是期望错 → 改测试（并在注释里写清为什么）
```

**不要看到红就改实现** —— 那会把正确的代码改坏去迎合错误的期望。

### 🔍 怎么发现自己违反了

| 症状 | 说明 |
|---|---|
| 你写的测试**从没失败过** | 反向验证一次，看它会不会红 |
| 测试里出现 `new Date()` / `time.Now()` / 随机数 | 不确定 → 做成参数注入 |
| 团队里有人说"这个用例偶尔失败，重跑就行" | **必须修**，否则整个套件失去意义 |
| 断言的是夹具里的静态值，而不是"发生了什么" | 恒为真 |
| 测试失败时你的第一反应是"改实现" | 先问是不是期望错了 |

> **本项目的硬规矩**：改了关键逻辑 → **必须**做反向验证，
> 并且把验证记录写进 `frontend/AGENTS.md` §5.8（那里有 10+ 条记录）。

### ⚖️ 什么时候可以打破

- 一次性的探索脚本不用写测试
- **但**凡是"以后还会跑、还会改"的代码，测试就是**你未来的自己**的保险

## 7. 工程习惯

### 原则一：**依赖越少越好**

本项目有一条硬规则：**加任何依赖之前先问**。

**理由不是保守，是三个很实际的代价**：

| 代价 | 说明 |
|---|---|
| **会出网、会花钱** | 本机装了依赖走的是**计费**代理 |
| **是长期的负担** | 依赖会升级、会有安全漏洞、会有 breaking change —— **都是你要维护的** |
| **可能根本不需要** | 大部分需求标准库就够了 |

**真实例子**：本项目需要解析 Prometheus 文本、解析 SSE 流，
**都没有引库，而是手写了 30 行左右的解析函数**。

> **养成这个反射**：想加依赖之前，先问
> **"我自己写要多少行？"** —— 如果答案是"几十行"，那就自己写。

### 原则二：**密钥永远不进代码仓库**

```bash
# ❌ 永远不要这样
const dbPassword = "medicore123"
```

**为什么？** GitHub 上**一直**有人在扫密钥，而且**删掉也没用** ——
Git 会保留历史，`git log` 一查就出来。

**✅ 本项目的做法**：
- 仓库里**不含任何密钥**，只有一个 `.env.example`（占位说明）
- 真的 `.env` 在 `.gitignore` 里
- 本地密钥用 `go run ./cmd/genlocal` **生成**（随机）
- 启动时还会**按特征拒绝**可预测的密钥（比如全是同一个字符、
  或者含有 `change-me`/`example` 这种占位词）

> **最后那条特别值得学**：它把"不要用弱密钥"这条**口头规矩**
> 变成了**程序启动就报错**的硬约束。**能自动化的规矩，就不要靠人记。**

### 原则三：注释解释**为什么**，不是**是什么**

```go
// ❌ 废话注释：代码已经说了
i++  // i 加一

// ✅ 有用的注释：解释为什么，以及不这样做会怎样
// 必须 KEEPTTL：裸 SET 会清掉 SETNX 设置的过期时间，
// 号源键就此变成永不过期的键，而 SETNX 也不会再刷新它。
redis.call('SET', key, cap, 'KEEPTTL')
```

**判断标准**：如果注释只是把代码翻译成中文，**删掉它**。
如果注释解释了"为什么是这个写法、不这么写会出什么事"，**留着**。

### 原则四：**代码是权威，文档可能过期**

本项目的 `AGENTS.md` §5.7 记着一件事：
> 文档里的路由清单**已经错过两次**。**代码一直是对的，错的是文档。**

**所以**：
- 需要接口清单 → **看代码**（`router.go`），不要照抄文档
- 文档和代码不一致 → 以**代码**为准，然后**顺手把文档改对**
- 你改了行为 → **同步改文档**（否则下一个被坑的人就是你）

### 原则五：**收尾动作才是主要失分点**

本项目统计过自己的失效模式，结论是：

> **设计判断都站得住，出错的是"写完不编译、写了不跑、断言恒为真"。**

翻译成日常习惯，就三条：

| 习惯 | 具体做法 |
|---|---|
| **① 每写完一个文件就编译** | 别攒到最后 —— 一次编译 50 个错误比 3 个难查得多 |
| **② 关键测试做反向验证** | 改坏实现 → 确认变红 → 改回来 |
| **③ 跑门槛** | `nub run lint` + `nub run test`，**两个都绿才算完** |

**为什么把这条放在最后？** 因为它最不起眼，但**命中率最高**。

### 🔍 怎么发现自己违反了

| 症状 | 说明 |
|---|---|
| 你在 `package.json` 里加了个包，但说不清"为什么非它不可" | 先问 |
| 仓库里能搜到密码、token、私钥 | 立刻处理，且**要换掉那些密钥** |
| 注释在重复代码 | 删掉或改成解释"为什么" |
| 你按文档写的代码跑不通 | 先怀疑文档 |
| 你交代码时没跑过测试 | 这是最常见的失分点 |

### ⚖️ 什么时候可以打破

- 紧急修线上 bug 时可以先上、后补测试 —— **但必须真的补**（并且记下来）
- 探索性的临时脚本不用管注释规范
- **但**"临时"的东西如果活过了一周，它就不再临时了 —— 该补的要补

## 8. 速查卡：十条最容易违反的

贴在显示器旁边用：

| # | 规则 | 违反了会怎样 |
|---|---|---|
| 1 | **前端校验只是为了体验，后端必须再校验一遍** | 用 Postman 就能绕过 |
| 2 | **`RequireRole` 不等于"这是他的数据"** | 越权读别人的数据（真实发生过） |
| 3 | **"先查再插"有并发竞态，用唯一索引** | 并发下插进重复数据 |
| 4 | **手写 JOIN 要自己加 `deleted_at IS NULL`** | 返回已删除的数据 |
| 5 | **判 JOIN 有没有结果用 `IS NOT NULL`，不是 `= 0`** | 换一列就出错 |
| 6 | **别把 `err.Error()` 直接返回给用户** | 泄漏内部细节 |
| 7 | **错误提示必须指向正确的解决动作** | 限流提示"密码错误"→ 用户越改越锁 |
| 8 | **测试里的时间/随机数要做成参数** | 偶发失败 → 大家开始"重跑就好" → 测试失去意义 |
| 9 | **写完关键测试，故意改坏实现看它红不红** | 恒为真的测试给你虚假安全感 |
| 10 | **交代码前跑 `nub run lint` 和 `nub run test`** | 最常见的失分点 |

## 9. 什么时候可以打破原则

**这一章最重要，请一定读完。**

初级工程师最常见的两个问题是：

| 问题 | 表现 |
|---|---|
| **不知道原则** | 写出上面那些反例 |
| **把原则当教条** | 给一行代码建三层、为不会并发的地方加锁、给临时脚本写 20 个测试 |

**成熟度的标志是知道"何时可以例外"。** 通用的判断方法：

| 问自己 | 如果答案是… |
|---|---|
| 这段代码会**长期存在**吗？ | 不会 → 可以简化 |
| 它会被**并发**调用吗？ | 不会 → 不用考虑竞态 |
| 数据**能指向某个人**吗？ | 不能 → 不用归属校验 |
| 出错时**有人会因此损失**吗？ | 不会 → 错误处理可以简单些 |
| 我**下周还会改**它吗？ | 会 → 补测试 |

**但有三条底线不建议打破**：

1. **密钥不进仓库** —— 泄漏一次就不可逆
2. **交代码前跑门槛** —— 这是纪律，不是技术判断
3. **关键逻辑做反向验证** —— 否则你不知道自己的测试有没有用
